# 03. Server-side prior art in other languages

Date: 2026-10-13. Scope: server-side architecture (language front end, type system, validation, execution, DataLoader, extensions, introspection, transports) for a from-scratch, fully typed, spec-complete GraphQL implementation targeting Dart 3.x (sealed classes, records, pattern matching, extension types; no runtime reflection in AOT/Flutter; build_runner/source_gen codegen; Dart macros were cancelled). The previous attempt, a line-by-line port of graphql-java, is treated as the baseline to move away from. Covers graphql-js v16/v17 (reference), graphql-java (briefly), Rust (apollo-rs in depth, async-graphql, juniper), Kotlin (graphql-kotlin, Apollo Kotlin internals and its KMP execution engine), Swift (Graphiti), C# (Hot Chocolate), Scala (Caliban, Sangria), TypeScript (Pothos, Grats, TypeGraphQL, Nexus, envelop/Yoga, @graphql-tools), Go (gqlgen), and the FP cluster (Haskell/OCaml/F#), included only where it adds a unique typing idea. Method: primary sources only. Source is read at a pinned commit (every GitHub link is a SHA permalink resolved via `gh api` on 2026-10-13), together with official docs and changelogs; key claims were re-fetched and spot-checked. Where something could not be verified, it says so. ✅ = take directly, ⚠️ = adapt for Dart's constraints, ❌ = avoid / wrong fit. Companion docs: 01 (spec and protocols), 02 (Dart ecosystem), 04 (client prior art), 05 (Dart language and platform).

## 0. In brief: the 16 most valuable patterns

1. **Use a hand-written, error-resilient recursive-descent parser with byte-offset spans.** graphql-js, apollo-parser and Apollo Kotlin all hand-write their parsers ([apollo-rs ARCHITECTURE.md#L35-L40](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/ARCHITECTURE.md#L35-L40)). Only apollo-parser *never throws*: errors go to a side list while the tree is still built ([`syntax_tree.rs#L58-L77`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-parser/src/parser/syntax_tree.rs#L58-L77)). graphql-js's throw-on-first-error is an open tooling complaint ([#1426](https://github.com/graphql/graphql-js/issues/1426)). (§2.1, §4.1)
2. **Use typestate for validation: `Valid<T>` with a crate-private constructor, propagated from schema to document.** `ExecutableDocument::validate(self, schema: &Valid<Schema>) -> Result<Valid<Self>, WithErrors<Self>>` ([apollo-compiler `validation/mod.rs#L63-L110`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/validation/mod.rs#L63-L110), [`executable/mod.rs#L417-L436`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/executable/mod.rs#L417-L436)). In Dart, use a `final class` with a private constructor, not an extension type. (§4.3)
3. **Write N independent validation rules and fuse them into one traversal.** graphql-js `visitInParallel` ([`visitor.ts#L412`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/visitor.ts#L412), used at [`validate.ts#L151`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/validation/validate.ts#L151)) gives you testable, toggleable rules with a single walk. (§2.4)
4. **Add a sync fast path in the executor: allocate nothing async unless a resolver actually returned a future.** graphql-js's `containsPromise` ([`execute.ts#L693-L724`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/execution/execute.ts#L693-L724)) is the template. graphql-java shows the cost of not doing this ([#3331](https://github.com/graphql-java/graphql-java/issues/3331)). In Dart this means `FutureOr<T>` throughout the engine. (§2.5, §3)
5. **Give pure synchronous resolvers a separate lane.** Hot Chocolate's `PureFieldDelegate` is documented as *"side-effect free and sync"*, next to `ValueTask FieldDelegate` ([`PureFieldDelegate.cs`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/HotChocolate/Core/src/Types/Resolvers/PureFieldDelegate.cs)). Dart codegen knows statically which fields are plain getters. (§10)
6. **Compose per-field middleware once, at schema build.** Use `FieldMiddleware = FieldDelegate Function(FieldDelegate next)`, folded into one delegate per field ([`FieldMiddlewareCompiler.cs`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/HotChocolate/Core/src/Types/Types/Helpers/FieldMiddlewareCompiler.cs)), never per request and never by monkey-patching resolvers (envelop's `on-resolve`). (§10, §16)
7. **Compile the operation into a plan and cache it, with single-flight compilation.** Hot Chocolate caches compiled operations by document id plus operation name and coalesces concurrent compilations ([`OperationCacheMiddleware.cs#L40-L57`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/HotChocolate/Core/src/Types/Execution/Pipeline/OperationCacheMiddleware.cs#L40-L57)). graphql-js v17 regressed by up to 50% from running its field-plan step on every request ([#4008](https://github.com/graphql/graphql-js/issues/4008)). (§2.6, §10)
8. **Design for incremental delivery from day one, but ship it behind an opt-in.** graphql-js v17 is GA, yet `@defer`/`@stream` are still outside `specifiedDirectives` ([`directives.ts#L361-L409`](https://github.com/graphql/graphql-js/blob/71606d736c79b77588a15b32b9c9497e397adae0/src/type/directives.ts#L361-L409)), and retrofitting them took a revert-and-replace of the whole incremental implementation followed by an executor split ([#4534](https://github.com/graphql/graphql-js/pull/4534), [#4537](https://github.com/graphql/graphql-js/pull/4537), [#4545](https://github.com/graphql/graphql-js/pull/4545)). (§2.6)
9. **Derive nullability from host types: bare `T` maps to `T!`, and `T?`/`Option`/`Optional` maps to nullable.** async-graphql, juniper, graphql-kotlin, Graphiti and Caliban all agree ([Graphiti `TypeProvider.swift#L47-L57`](https://github.com/GraphQLSwift/Graphiti/blob/20c8d0229646c4a022aeb8250d35fde51240bf1b/Sources/Graphiti/Definition/TypeProvider.swift#L47-L57)). Go needs a runtime `InvalidNullError` because it can't do this ([gqlgen `invalid_null.go`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/graphql/invalid_null.go)). (§5, §9, §17)
10. **Map closed sum types to GraphQL enums, unions and interfaces.** Caliban's rule ([`SumSchema.scala#L33-L39`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala-3/caliban/schema/SumSchema.scala#L33-L39)): a sealed type whose cases have no fields becomes an ENUM, one whose cases have fields becomes a UNION, and one marked `@GQLInterface` becomes an INTERFACE. In Dart, `sealed class` plus a generated exhaustive `resolveType` switch. (§11)
11. **Generate resolver obligations only for fields that can't be auto-bound.** gqlgen's generated `XResolver` interface contains only forced or unbindable fields ([`_examples/config/generated.go#L29-L85`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/config/generated.go#L29-L85)). The Dart analogue is generated `abstract class`es that the user `extends`. (§17)
12. **Annotate plain classes and read them at build time, never at runtime.** Grats (Rust/oxc static analysis, zero runtime code: [how-grats-works](https://github.com/captbaritone/grats/blob/5a6b449e7f56e3d293190a37760f117d3baf835d/website/docs/06-faq/03-how-grats-works.md#L9-L21)), async-graphql proc-macros and Hot Chocolate's Roslyn generator all do this. TypeGraphQL (`reflect-metadata`) and graphql-kotlin (`callBy`) show why the runtime alternative is lossy and slow, and it is impossible in AOT Dart. (§5, §7, §10, §14, §15)
13. **Wrap each request phase in an explicit `next`-chained extension.** async-graphql's `Extension` uses `request/parse_query/validation/execute/resolve(…, next)` ([`extensions/mod.rs#L380-L439`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/extensions/mod.rs#L380-L439)), and envelop's `Plugin` has `onParse`/`onValidate`/`onExecute`/`onSubscribe`. Avoid graphql-java's 20-hook `Instrumentation`, which was deprecated and then partly walked back. (§3, §5, §16)
14. **Treat directives as typed middleware slots.** gqlgen generates `DirectiveRoot{ HasRole func(ctx, obj, next, role Role) }` ([`generated.go#L35-L38`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/generated.go#L35-L38)), so each directive is implemented once and wired wherever it is applied, with arguments already coerced. (§17)
15. **Provide DataLoader in two variants, request-scoped and generated from a function.** GreenDonut has `BatchDataLoader` (map) and `GroupedDataLoader` (lookup), plus a `[DataLoader]` source generator ([`DataLoaderAttribute.cs`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/GreenDonut/src/GreenDonut.Abstractions/Attributes/DataLoaderAttribute.cs)). Sangria shows that batching works on *eager* futures ([deferred resolution](https://sangria-graphql.github.io/learn/#deferred-value-resolution)); ZQuery's automatic batching needs laziness that Dart lacks. (§10, §11, §12)
16. **Stack the server in four layers: engine, phase plugins, a generic Request/Response adapter, and the GraphQL-over-HTTP binding.** Transports and APQ are separate plugins (Yoga [`plugins/types.ts`](https://github.com/graphql-hive/graphql-yoga/blob/9d29d6e9a9fdf353082fa036f51255ae727199af/packages/graphql-yoga/src/plugins/types.ts), [APQ plugin](https://github.com/graphql-hive/graphql-yoga/blob/9d29d6e9a9fdf353082fa036f51255ae727199af/packages/plugins/apq/src/index.ts)). (§16)

## 2. graphql-js v16 and v17: the reference implementation

Pinned: **v16** at tag `v16.14.2` → [`dca5b4d`](https://github.com/graphql/graphql-js/commit/dca5b4d4507dc3d324dc83aa39f359db3ab1a141); **v17** at tag `v17.0.2` → [`71606d7`](https://github.com/graphql/graphql-js/commit/71606d736c79b77588a15b32b9c9497e397adae0). Docs: <https://graphql.org/graphql-js/>.

> **Status correction (2026).** v17 is no longer an alpha. It went GA on 2026-06-15 ([announcement](https://graphql.org/blog/2026-06-15-introducing-graphql-js-v17/)), and the repo's default branch is now `17.x.x` (checked with `gh api repos/graphql/graphql-js`). **However, `@defer`/`@stream` ship only as an opt-in experiment inside the stable release.** `GraphQLDeferDirective` and `GraphQLStreamDirective` are *not* in `specifiedDirectives`. Their doc comments say they are *"exported for schemas that explicitly opt in to incremental delivery"* ([`directives.ts#L361-L409`](https://github.com/graphql/graphql-js/blob/71606d736c79b77588a15b32b9c9497e397adae0/src/type/directives.ts#L361-L409)). The spec text is still an open PR ([graphql-spec#1110](https://github.com/graphql/graphql-spec/pull/1110)), governed by [graphql/defer-stream-wg](https://github.com/graphql/defer-stream-wg).

### 2.1 Lexer and parser
- **Hand-written recursive descent.** `class Lexer` ([`lexer.ts#L35`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/lexer.ts#L35)) is a cursor that builds a doubly linked list of `Token`s, so lookahead is cached. The specialised readers are `readNumber`, `readString`, `readBlockString` and `readName` (L457–L915). `class Parser` ([`parser.ts#L324`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/parser.ts#L324)) has one `parseX()` per production. A shared `node()` helper only stamps `.loc` onto a plain object literal ([`#L1775-L1784`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/parser.ts#L1775-L1784)). ✅
- **Comments are dropped.** `COMMENT` tokens are skipped inside `lookahead()`. [Issue #2241 "Maintain comments when parsing schema"](https://github.com/graphql/graphql-js/issues/2241) is still open. ❌ for tooling (contrast apollo-rs, §4).
- **No error recovery.** Every failure is `throw syntaxError(…)`, so the first error aborts the parse. [Issue #1426 "Parser for Language Services and Editor Tooling"](https://github.com/graphql/graphql-js/issues/1426) is still open. ❌
- **Spans.** `Location` holds `start`/`end` offsets plus start and end tokens ([`ast.ts#L11-L73`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/ast.ts#L11)). Line and column come from `getLocation()`, which re-scans the body with a regex on every call ([`location.ts`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/location.ts)). ✅ Keep the offsets. ⚠️ Build a line-start table once per `Source` instead of re-scanning.

### 2.2 AST and data model
`ASTNode` is a union of about 40 interfaces, each discriminated by a string-valued `kind` ([`ast.ts#L192-L241`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/ast.ts#L192), [`kinds.ts#L4`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/kinds.ts#L4)). Nodes are plain objects with no interning, no ids and no typestate: a parsed `DocumentNode` and a validated one have the same type. The generic `visit()`/`ASTVisitor` (including a per-`Kind` map form, [`visitor.ts#L10-L24`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/visitor.ts#L10)) is used by validation, `TypeInfo`, `separateOperations` and the printer, which is itself an `ASTReducer`. ✅ Keep one traversal abstraction reused everywhere. ⚠️ In Dart, a `sealed class Node` hierarchy gives an exhaustive `switch` that TypeScript's `kind` narrowing does not enforce. ❌ No validated/unvalidated distinction (§4 shows the fix).

### 2.3 Schema definition and resolver typing
Schemas are built at runtime from config objects: `GraphQLObjectType` ([`definition.ts#L2044`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/definition.ts#L2044)) and `GraphQLSchema` ([`schema.ts#L181`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/schema.ts#L181)). The resolver type is `GraphQLFieldResolver<TSource, TContext, TArgs = any, TResult = unknown>` ([`definition.ts#L2505-L2515`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/definition.ts#L2505)). In `GraphQLFieldConfig` ([`#L2564-L2581`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/definition.ts#L2564)), **the declared `type` is never linked to `TResult`**. A field typed `String!` whose resolver returns a `number` compiles, and the mismatch shows up only in `completeValue` → `serialize()` at runtime. ✅ Keep the `(source, args, context, info) → value` contract. ❌ Do not leave the GraphQL type and the resolver result type unlinked. Closing that gap is the main reason to use codegen in Dart (§19.3).

### 2.4 Validation: N visitor rules fused into one traversal
There is one file per rule under `src/validation/rules/` (31 files). Each is `function XRule(context: ValidationContext): ASTVisitor`; for example, `ScalarLeafsRule` is about 15 lines with one `Field(node)` handler ([source](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/validation/rules/ScalarLeafsRule.ts)). `validate()` runs **all rules in one walk**:

```ts
// validate.ts#L149-L151 (verified)
// This uses a specialized visitor which runs multiple visitors in parallel,
// while maintaining the visitor skip and break API.
const visitor = visitInParallel(rules.map((rule) => rule(context)));
```

[`validate.ts#L151`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/validation/validate.ts#L151). `visitInParallel` ([`visitor.ts#L412-L471`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/language/visitor.ts#L412)) builds one merged enter/leave function per `Kind`. A per-rule `skipping[]` array means one rule's `false` (skip subtree) or `BREAK` does not stop the other rules. `visitWithTypeInfo` adds parent-type and expected-type tracking, so no rule has to recompute it. `maxErrors` aborts early with a sentinel throw.

✅✅ **Take.** Rules are independent, easy to test, and individually toggleable (users add `depthLimit`, `noIntrospection`, and so on), yet there is only one traversal. In Dart a rule can be an object with `enter(Node)`/`leave(Node)` methods that `switch` over the sealed node type, combined by a `ParallelVisitor`. ⚠️ Port **`OverlappingFieldsCanBeMerged`** using the faster algorithm from [issue #2185](https://github.com/graphql/graphql-js/issues/2185) (from Sangria, still not merged into graphql-js), not graphql-js's own version.

### 2.5 Execution engine (v16 `execute.ts`)
- **Field collection.** `collectFields()` ([`collectFields.ts`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/execution/collectFields.ts)) flattens fragments into `Map<responseKey, FieldNode[]>` and applies `@skip`/`@include`. v16 memoises `collectSubfields` with a `memoize3` keyed by `(exeContext, returnType, fieldNodes)` ([`execute.ts#L70`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/execution/execute.ts#L70)), which caches within a request but **not across requests**, because `exeContext` is new each time.
- **Serial mutations.** `executeOperation` sends `mutation` to `executeFieldsSerially`, which awaits each root field through `promiseReduce`. Queries and subscriptions go to `executeFields`.
- **Sync fast path (verified).** `executeFields` tracks `let containsPromise = false` (L693) and returns the plain object *"If there are no promises"* (L723-L724). `completeListValue` does the same for lists (L989-L1038). An all-synchronous query allocates **no** Promise. ✅✅ This is the template for a Dart `FutureOr` executor. Dart cannot skip the check: `FutureOr<T>` is a static union, so the engine still needs `if (r is Future)` branches at each level. The win is that sync resolvers never create a `Future`, and Dart's type system makes the distinction explicit rather than duck-typed.
- **Errors and null bubbling.** `completeValue()` implements the spec's value completion. Errors are wrapped by `locatedError()` with node and path ([`locatedError.ts#L34`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/error/locatedError.ts#L34)). `handleFieldError()` rethrows if the return type is non-null, so the error bubbles to the nearest nullable parent; otherwise it records the error and returns `null`. ✅ Port nearly verbatim.
- **Subscriptions.** `subscribe()` calls `createSourceEventStream`, then `mapAsyncIterator(resultOrStream, mapSourceToResponse)` runs `execute` once per event ([`subscribe.ts#L170-L191`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/execution/subscribe.ts#L170-L191)). ✅ In Dart this is `Stream.asyncMap`.

### 2.6 v17: incremental delivery and a rebuilt executor
- New layout: `execution/Executor.ts` and `ExecutorThrowingOnIncremental.ts`, plus [`execution/incremental/`](https://github.com/graphql/graphql-js/tree/71606d736c79b77588a15b32b9c9497e397adae0/src/execution/incremental) containing `buildExecutionPlan.ts`, `IncrementalExecutor.ts`, `IncrementalPublisher.ts`, `WorkQueue.ts`, `Queue.ts` and `Computation.ts`. Entry points: `execute()` (single result, *throws* if `@defer`/`@stream` appear), `experimentalExecuteIncrementally()`, and `legacyExecuteIncrementally()` for the old response shape ([announcement](https://graphql.org/blog/2026-06-15-introducing-graphql-js-v17/)).
- **The plan step.** [`buildExecutionPlan.ts`](https://github.com/graphql/graphql-js/blob/71606d736c79b77588a15b32b9c9497e397adae0/src/execution/incremental/buildExecutionPlan.ts) splits a grouped field set into the initial set plus `Map<DeferUsageSet, GroupedFieldSet>`. This decides which fields ship now and which ship in each deferred payload, and it de-duplicates fields shared between payloads.
- **Publishing.** `IncrementalPublisher` turns a `WorkQueue` of events into `{data, pending, hasNext}`, then a sequence of `{incremental, completed, pending, hasNext}`. That is the response format redesigned in [defer-stream-wg#69](https://github.com/graphql/defer-stream-wg/discussions/69).
- **Churn worth learning from.** On 2026-01-27, [#4534](https://github.com/graphql/graphql-js/pull/4534) *"temporarily revert incremental delivery"* (*"will need to fix abort and merge back incremental delivery"*) removed the existing implementation. Seventeen minutes later, [#4537](https://github.com/graphql/graphql-js/pull/4537) "Reference implementation of defer and stream spec" (*"extracted from work on branch `next`"*) landed in its place. A week later, [#4545](https://github.com/graphql/graphql-js/pull/4545) "extract IncrementalExecutor from Executor" split the engine into a base `Executor` and an incremental one; merge times were checked with `gh api`. Separately, [#4008 "Current main is up to 50% slower than previous major version"](https://github.com/graphql/graphql-js/issues/4008) traced a v17-alpha regression to the new field-plan step that runs after `collectFields`.
- ⚠️ **Adapt.** Design the executor from day one so field collection produces *grouped field sets with defer usage*, even before `@defer` ships. That avoids graphql-js's retrofit. ✅ Cache the plan per (document, operation) so the cost behind #4008 is paid once, not per request (Hot Chocolate does this, §10). ✅ Keep incremental delivery behind a separate entry point that returns `Stream<IncrementalResult>`, and make plain `execute()` reject `@defer`/`@stream` unless the schema opts in.

### 2.7 DataLoader, extensions, introspection
- **DataLoader** is not in core. The [`n1-dataloader` docs page](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/website/pages/docs/n1-dataloader.mdx) points to the separate [graphql/dataloader](https://github.com/graphql/dataloader) package. ✅ Keep it in a separate package.
- **Extensions.** There is no plugin system, only the `fieldResolver`/`typeResolver` arguments to `execute()`. Everything cross-cutting lives above the core (envelop, §16). ⚠️ A Dart core should expose typed hook points (§19) and still leave policy to plugins.
- **Introspection** is ordinary types. `__Schema` and `__Type` are `GraphQLObjectType`s ([`introspection.ts#L39`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/introspection.ts#L39), [`#L236`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/introspection.ts#L236)), and the `__schema` meta-field is `resolve: (_s, _a, _c, { schema }) => schema` ([`#L553-L562`](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/src/type/introspection.ts#L553)). ✅ Introspection should use the same executor, with resolvers over the schema model.

### 2.8 Testing and performance
- Changes are spec-gated (*"only changes which comply with this spec will be considered"*, [CONTRIBUTING.md](https://github.com/graphql/graphql-js/blob/dca5b4d4507dc3d324dc83aa39f359db3ab1a141/.github/CONTRIBUTING.md)). Other implementations port graphql-js algorithms explicitly; graphql-java's [`VariablesTypesMatcher.java`](https://github.com/graphql-java/graphql-java/blob/master/src/main/java/graphql/validation/VariablesTypesMatcher.java) says it *"was inspired from the reference graphql-js implementation"*. ✅ **Port the `src/**/__tests__` corpus** (each validation rule's tests plus execution tests such as nonnull, lists, variables, abstract types and mutations) as the Dart conformance suite.
- Maintainers publish no benchmark numbers. The verifiable performance history is [#4008](https://github.com/graphql/graphql-js/issues/4008) (field-plan cost), [#2185](https://github.com/graphql/graphql-js/issues/2185) (overlapping-fields scaling) and [#3648](https://github.com/graphql/graphql-js/issues/3648) (an ES5→ES6 output regression).

## 3. graphql-java (brief): why a direct port maps badly onto Dart

Pinned: [`graphql-java/graphql-java@4c09620`](https://github.com/graphql-java/graphql-java/commit/4c096208ba7203c92ed6617ddfdc35653c8aca11) (master, 2026-10-09).

graphql-java is a faithful, battle-tested engine, but most of its *shape* exists to compensate for things Java lacks. Dart has all four of those features, so a line-by-line port brings over Java's workarounds and leaves Dart's own strengths unused.

| graphql-java mechanism | What Java gap it compensates for | Dart has natively | Verdict |
|---|---|---|---|
| Runtime builders everywhere: `GraphQLObjectType.newObject()…build()` ([`GraphQLObjectType.java#L242-L252`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/schema/GraphQLObjectType.java#L242-L252)), `GraphQLSchema.newSchema()` ([`GraphQLSchema.java#L745-L806`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/schema/GraphQLSchema.java#L745-L806)) | No named/optional/required constructor parameters, no literals | Named + `required` parameters, `const` constructors, records | ❌ The port is all ceremony. Nothing is checked until `.build()` throws. |
| `DataFetcher<T> { T get(DataFetchingEnvironment env) }` ([`DataFetcher.java`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/schema/DataFetcher.java)) with `<T> T getSource()`, `<T> T getArgument(String)`, `<T> T getContext()` ([`DataFetchingEnvironment.java#L45-L97`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/schema/DataFetchingEnvironment.java#L45)) | Erased generics, so parent, args and context arrive as unchecked casts | Reified generics, records for args | ❌ The type parameter covers only the result. Dart can type parent, args, context *and* result. |
| `GraphQLNonNull.nonNull(type)` wrapper ([`GraphQLNonNull.java#L21-L32`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/schema/GraphQLNonNull.java#L21)), decoupled from the resolver's Java return type | No non-null types | Sound null safety (`T` vs `T?`) | ❌ Derive `!` from the Dart type. Don't keep a parallel wrapper system. |
| Every field goes through `CompletableFuture` ([`ExecutionStrategy.java#L135`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/execution/ExecutionStrategy.java#L135), [`AsyncExecutionStrategy.java#L25`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/execution/AsyncExecutionStrategy.java#L25)) | No sync/async union type | `FutureOr<T>` | ❌ See below. |
| `Instrumentation`: about 20 `beginX` hooks returning `InstrumentationContext` ([`Instrumentation.java#L43`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/execution/instrumentation/Instrumentation.java#L43)) | (none; this is design churn) | n/a | ⚠️ Keep the idea of phase hooks, not this interface. |

**Evidence that the async model is a cost the maintainers are still paying down.** [PR #3480](https://github.com/graphql-java/graphql-java/pull/3480) (2024) says: *"if the above field returned was a materialised object… we would create 4 CompletableFutures… CF are not slow inherently — but they are memory allocation."* [Issue #3331](https://github.com/graphql-java/graphql-java/issues/3331) (still open) says: *"every value returned for a graphql field is encapsulated into a CF."* The current workaround is a `@DuckTyped` convention: methods return `Object`, which may be a CF or a plain value, and callers check with `instanceof` ([`ExecutionStrategy.java#L202`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/execution/ExecutionStrategy.java#L202), introduced in [`d854425`](https://github.com/graphql-java/graphql-java/commit/d854425ef5365ed8bdbcf1098c40738b66e4759b)). That is `FutureOr<T>` reinvented by hand, without static checking.

**Instrumentation churn.** The API predates async support. Maintainer [issue #890](https://github.com/graphql-java/graphql-java/issues/890) (2018) says: *"The Instrumentation classes … were added BEFORE we added the CompletableFuture async support."* At the pinned commit, `beginFieldFetch` is `@Deprecated(since = "2024-04-18")` in favor of `beginFieldFetching` ([`Instrumentation.java#L221-L223`](https://github.com/graphql-java/graphql-java/blob/4c096208ba7203c92ed6617ddfdc35653c8aca11/src/main/java/graphql/execution/instrumentation/Instrumentation.java#L221-L223)). Commit [`b0b3b6d`](https://github.com/graphql-java/graphql-java/commit/b0b3b6d955243b739cb028ef01137ed2e1997310) "Removed the deprecated Instrumentation methods" was partly walked back by [`93489b8`](https://github.com/graphql-java/graphql-java/commit/93489b8e9fd1ea912cc944edaec25ad6b6dd2b77) "Putting createState back into Instrumentation".

**What is worth keeping:** the conformance knowledge (its validation and execution test corpus) and the general idea of phase-level instrumentation. Its type-system and execution *architecture* should not be kept.

## 4. Rust: apollo-rs (`apollo-parser` + `apollo-compiler`): deep study

Pinned: [`apollographql/apollo-rs@b7eee5c`](https://github.com/apollographql/apollo-rs/commit/b7eee5c8990fb9741a1236514d868681aeb28fec) (main, 2026-09-30). That commit has `apollo-parser 0.8.6` and `apollo-compiler 1.33.0`. The repo has no ADR folder. The design document is [`ARCHITECTURE.md`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/ARCHITECTURE.md), cross-checked against [`apollo-compiler/CHANGELOG.md`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/CHANGELOG.md).

This is the most directly relevant prior art for the language and validation layers. The two crates are separate tiers. **apollo-parser** owns a lossless CST. **apollo-compiler** lowers that CST *once* into a trivia-free AST and then into high-level `Schema` / `ExecutableDocument` models, and it keeps no CST afterwards.

### 4.1 Lexer and parser
- **Hand-written recursive descent.** From [`ARCHITECTURE.md#L35-L40`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/ARCHITECTURE.md#L35-L40): *"recursive-descent parsers make it easier to output helpful diagnostics. They perform well and they're easier to maintain."* The lexer is a hand-rolled state machine (`crates/apollo-parser/src/lexer/mod.rs`). The parser has one function per production under `crates/apollo-parser/src/parser/grammar/*.rs`. Only the *typed accessor* layer (`cst::Field::name()` and similar) is generated, by an `xtask`, from an `ungrammar` file. That grammar never drives parsing. ✅ Use a hand-written parser plus generated typed accessors. Dart can generate the accessors with a one-off script, not `build_runner`.
- **Lossless CST on `rowan`** ([`apollo-parser/Cargo.toml#L21`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-parser/Cargo.toml#L21), rowan 0.16, the rust-analyzer tree library). Whitespace and comments are pushed into the tree as `Whitespace`/`Comment` tokens (`Parser::push_ignored`, [`parser/mod.rs#L235-L244`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-parser/src/parser/mod.rs#L235-L244)), so the concatenated token text reproduces the source byte for byte. That makes formatters, codemods and IDE features possible, which a trivia-stripping AST (graphql-js style) cannot support. ✅ Take for tooling. ⚠️ Rowan's green/red interning is a real investment. A fully materialised immutable CST that is still lossless and byte-spanned gets most of the value.
- **Error resilience.** *"the lexing step never fails"*. Syntax errors *"are added to parser's error vector while the parser carries on parsing"* ([`ARCHITECTURE.md#L50-L71`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/ARCHITECTURE.md#L50-L71)). The mechanism is `err_and_pop`, which splices a `SyntaxKind::ERROR` token in place and continues ([`parser/mod.rs#L324-L345`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-parser/src/parser/mod.rs#L324-L345)). The result `SyntaxTree` bundles the green tree and `errors: Vec<Error>` ([`syntax_tree.rs#L58-L77`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-parser/src/parser/syntax_tree.rs#L58-L77)). Its doc test shows one error *and* a walkable valid remainder. ✅ Take: always return a tree, keep errors in a side list, use an `error` node kind, and never throw from the parse loop. This gives multiple diagnostics per parse and partial trees for editors.
- **Byte-offset spans.** apollo-compiler's `SourceSpan { file_id, text_range: TextRange }` stores byte offsets. `LineColumn` is a separate type computed lazily by `line_column_range(&SourceMap)` only when rendering ([`parser.rs#L73-L90`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/parser.rs#L73-L90), [`node.rs#L86-L89`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/node.rs#L86-L89)). ✅ Take: an `(int start, int end)` span plus a lazy line/column conversion at diagnostic time.

### 4.2 Data model: CST → AST → Schema/ExecutableDocument
- **Lowering.** `Document::from_cst` walks the typed CST once into an owned `ast::Document` ([`ast/from_cst.rs`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/ast/from_cst.rs)). Nodes that fail to convert are skipped because a parse error already covers them. The AST is *"faithful to the syntactic grammar, except that ignored tokens … are not preserved. These documents may or may not be valid"* ([`ast/mod.rs#L1-L10`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/ast/mod.rs#L1-L10)). The AST then builds `Schema` and `ExecutableDocument` (`schema/from_ast.rs`, `executable/from_ast.rs`). ✅ Take the three tiers. ✅ Separate the "syntactic AST" (formatter, printer, transforms) from the "semantic model" (validator, executor).
- **Storage.** The exact struct is `Schema { sources, schema_definition: Node<SchemaDefinition>, directive_definitions: IndexMap<Name, Node<DirectiveDefinition>>, types: IndexMap<NamedType, ExtendedType> }` ([`schema/mod.rs#L101-L128`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/schema/mod.rs#L101-L128)). `ExtendedType` is a closed enum over Scalar, Object, Interface, Union, Enum and InputObject. `Node<T>` is a `triomphe::Arc` with the `SourceSpan` in a header, which gives shared subtrees and copy-on-write via `make_mut` ([`node.rs#L13-L46`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/node.rs#L13-L46)). **There is no integer-ID arena.** `typed_arena` appears only locally inside the `FieldsInSetCanMerge` algorithm ([`executable/validation.rs#L33-L38`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/executable/validation.rs#L33-L38)). ✅ Take order-preserving name maps (Dart's default `LinkedHashMap`) and a sealed `ExtendedType`. ⚠️ Dart's GC already provides Arc-like sharing, so don't build an arena unless profiling one specific algorithm calls for it.
- **The salsa lesson.** Pre-1.0 apollo-compiler was a salsa (incremental query database) "compiler" with `create_schema`/ids. 1.0 was *"a near-complete rewrite"* ([`CHANGELOG.md#L1369-L1383`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/CHANGELOG.md#L1369-L1383)). Beta.14 then shipped **"Remove Salsa database for 1.2× ~ 2× validation speed … We were not taking advantage of caching it provides"** ([`CHANGELOG.md#L727-L741`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/CHANGELOG.md#L727-L741), [PR #838](https://github.com/apollographql/apollo-rs/pull/838)). ❌ Avoid an incremental query database in the core. An LSP can add caching on top later.

### 4.3 `Valid<T>` typestate (the key API idea)
`#[repr(transparent)] pub struct Valid<T>(pub(crate) T);` ([`validation/mod.rs#L63-L65`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/validation/mod.rs#L63-L65)). The field is crate-private. It has `Deref` but **no `DerefMut`**, `into_inner()` to drop the guarantee before mutating, and an explicit, loudly named `Valid::assume_valid` escape hatch ([`#L77-L110`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/validation/mod.rs#L77-L110)). The real constructors are:

```rust
Schema::validate(self) -> Result<Valid<Schema>, WithErrors<Schema>>                       // schema/mod.rs#L444
ExecutableDocument::validate(self, schema: &Valid<Schema>) -> Result<Valid<Self>, WithErrors<Self>>  // executable/mod.rs#L430
```

The guarantee **propagates**: you cannot validate a document without a `&Valid<Schema>`. The failure side, `WithErrors { partial: T, errors: DiagnosticList }` ([`#L196-L205`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/validation/mod.rs#L196-L205)), returns the partial model along with the diagnostics.

✅ **Take, in Dart, as a `final class` with a private constructor, not an extension type.** An extension type's constructor can be invoked on any `Schema`, so privacy would only be a convention. A class with a library-private `_` constructor is enforced by the compiler.

```dart
final class ValidSchema {
  const ValidSchema._(this.schema);
  final Schema schema;                          // read-only view; Schema itself immutable
  static ValidationResult<ValidSchema> validate(Schema s) => …; // only public route
  factory ValidSchema.assumeValid(Schema s) = ValidSchema._;    // loud escape hatch
}
// Executor API: execute(ValidSchema schema, ValidDocument doc, …)
// Document validation: ValidDocument.validate(Document d, {required ValidSchema schema})
```

### 4.4 Validation architecture
Validation is organised **by construct, with direct function calls and no visitor/rule registry**. [`schema/validation.rs#L21-L41`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/schema/validation.rs#L21-L41) is a single `match` over `ExtendedType`. `validate_executable_document` calls `validate_operation_definitions`, `validate_fragments_used`, `validate_defer`, `validate_subscription` and a dedicated `FieldsInSetCanMerge` struct ([`executable/validation.rs#L12-L50`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/src/executable/validation.rs#L12-L50)). Errors accumulate in a `&mut DiagnosticList`. ⚠️ This is the counterpoint to graphql-js's visitor rules (§2): when you validate a *typed semantic model* rather than a generic AST, the language's `match` *is* the dispatch. See §19 for how Dart combines the two.

### 4.5 Downstream and testing
Apollo Router uses the validator at scale (*"Enables large-scale production deployment of apollo-compiler's validation implementation"*, [`CHANGELOG.md#L695`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/crates/apollo-compiler/CHANGELOG.md#L695)). Rover uses it for schema diagnostics, and the sibling `apollo-smith` crate fuzzes both crates ([`ARCHITECTURE.md`](https://github.com/apollographql/apollo-rs/blob/b7eee5c8990fb9741a1236514d868681aeb28fec/ARCHITECTURE.md)). ✅ Take grammar-aware fuzzing (a Dart `graphql_smith`) as a conformance tool.

apollo-rs has **no executor or resolvers**. Sections 5 and 6 cover those for Rust.

## 5. Rust: async-graphql

Pinned: [`async-graphql/async-graphql@82cd1f1`](https://github.com/async-graphql/async-graphql/commit/82cd1f15c2a66c6134be6b93e3ac6331847934c6) (master, 2026-04-21). Book: <https://async-graphql.github.io/async-graphql/>.

**Parser and AST.** async-graphql has its own `async-graphql-parser` crate. This study did not go deep on it because apollo-rs (§4) is the better parser reference.

**Schema definition: annotations plus compile-time codegen (proc-macros).** Plain data types use `#[derive(SimpleObject)]` ([`derive/src/simple_object.rs#L31`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/simple_object.rs#L31)). Types with resolver logic use `#[Object]` on an `impl` block ([`derive/src/object.rs#L23`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/object.rs#L23)). `#[derive(Union)]`/`#[derive(Interface)]` accept **only Rust enums** (*"Union can only be applied to an enum."*, [`union.rs#L23-L24`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/union.rs#L15-L24)), so a closed sum type is the union. The macros emit `create_type_info(registry)` per type, which registers `MetaField`s from `<Ret as OutputType>::create_type_info` ([`object.rs#L645-L653`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/object.rs#L645-L653), [`#L872`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/object.rs#L872)). `Schema::build` calls those functions to fill the registry ([`src/schema.rs#L435-L440`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/schema.rs#L435-L440)).
- ✅ Take the approach of reading annotated source at build time and emitting registration and resolver glue. That is exactly `source_gen` over `package:analyzer`.
- ⚠️ The difference: proc-macros expand inline in one `rustc` pass, while `build_runner` is a separate step that writes `.g.dart` to disk. The analyzer shows errors until the first build, and generated files churn.
- ✅ Take the split between trivial and custom types (`SimpleObject` vs `#[Object]`; juniper has the same split, §6).
- ✅ A Dart `sealed class` hierarchy is the exact analogue of the enum-backed union/interface.

**Nullability and lists.** `Option<T>` is nullable, bare `T` is non-null, and `Vec<T>` is a list ([book: quickstart](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/docs/en/src/quickstart.md#L16)). ✅ Take this as is.

**Typed resolvers.** Inside `#[Object]`, the parent is the `&self` receiver, arguments are ordinary typed function parameters, and a parameter of type `Context<'_>` is recognised by name ([`object.rs#L120`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/object.rs#L120)). `#[graphql(desc = …)]` becomes the argument description ([`#L489-L491`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/derive/src/object.rs#L489-L491)). Request data is a `TypeId`-keyed `FxHashMap<TypeId, Box<dyn Any>>` with typed retrieval `ctx.data::<T>()` ([`src/context.rs#L58`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/context.rs#L58)). ✅ Dart equivalent: a `Map<Type, Object>`-backed context with `T get<T>()`. ⚠️ Prefer a typed, generated context class where possible (see §16 on envelop context typing).

**Validation.** It follows the classic visitor-rule style (graphql-js lineage). Depth and complexity limits run at **validation time**, so an over-limit query never starts executing. They are configured with `.limit_depth(n)`/`.limit_complexity(n)` and per-field `#[graphql(complexity = "count * child_complexity")]` ([book: depth & complexity](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/docs/en/src/depth_and_complexity.md)). ✅ Take: an `@Cost(…)` annotation in which codegen emits a per-field cost function, checked by a validation rule.

**Execution.** It is async-native, with no separate sync fast path: `resolve_field_async` and `resolve_simple_field_value` are both `async fn` ([`resolver_utils/object.rs`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/resolver_utils/object.rs)). Query and mutation share one `resolve_container_inner(…, parallel: bool)`. When `parallel` is true it uses `try_join_all`; otherwise it awaits fields sequentially ([`resolver_utils/container.rs#L128-L194`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/resolver_utils/container.rs#L128-L194)). ✅ Take the one-flag split between serial mutations and parallel queries. ⚠️ Rust futures are cheap, stack-allocated state machines. A Dart `Future` is a heap object scheduled through the microtask queue, so Dart needs the `FutureOr` fast path that async-graphql can skip (§2, §10).

**DataLoader (built in).** The trait is `Loader<K> { type Value; type Error; fn load(&self, keys: &[K]) -> impl Future<Output = Result<HashMap<K, Self::Value>, Self::Error>> }` ([`src/dataloader/mod.rs#L122-L139`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/dataloader/mod.rs#L122-L139)). `DataLoader<T, C = NoCache>` collects `load_one` calls within a tick into a single `load` call ([`#L194`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/dataloader/mod.rs#L194)). Loaders are registered with `.data(DataLoader::new(…))` and fetched through the same context bag ([book: dataloader](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/docs/en/src/dataloader.md)). ✅ Take as `abstract class BatchLoader<K, V> { Future<Map<K, V>> load(List<K> keys); }`, using the same request context and needing no new mechanism.

**Extensions: an explicit `next` onion over every phase.**

```rust
trait Extension {
  async fn request(&self, ctx, next: NextRequest) -> Response;
  async fn prepare_request(..); async fn parse_query(..); async fn validation(..);
  async fn execute(..); fn subscribe(..);
  async fn resolve(&self, ctx, info, next: NextResolve) -> ServerResult<Option<Value>>;
}
```

Every default body is `next.run(…)` ([`src/extensions/mod.rs#L380-L439`](https://github.com/async-graphql/async-graphql/blob/82cd1f15c2a66c6134be6b93e3ac6331847934c6/src/extensions/mod.rs#L380-L439)). The built-ins include tracing, Apollo tracing, an analyzer (complexity), Apollo persisted queries and a logger (`src/extensions/*.rs`). ✅ Take: a single interface covers both request-level and per-field (`resolve`) interception. ⚠️ A per-field `resolve` hook that is always present costs a closure plus a `Future` per field even when no extension is installed. In Dart, compile the chain only when non-empty (see §10's per-field fold).

**Introspection.** It is served from the same macro-built `Registry`. ✅ Use one source of truth.

**Testing and performance.** There is a large `tests/` directory (introspection, interface, union, federation, subscription, variables, and more). **No graphql-js fixture port could be verified**; the README's "fully specification compliant" claim is not backed by a ported suite. The only throughput figures are unofficial third-party numbers ([tailcallhq/benchmarks](https://github.com/tailcallhq/benchmarks): about 43k req/s for async-graphql against about 41k for juniper on a `hello` field). Treat them as indicative only.

- **Field middleware compiled once.**

  ```csharp
  public delegate ValueTask FieldDelegate(IMiddlewareContext context);          // FieldDelegate.cs
  public delegate FieldDelegate FieldMiddleware(FieldDelegate next);            // FieldMiddleware.cs
  public delegate object? PureFieldDelegate(IResolverContext context);          // PureFieldDelegate.cs
  ```

  `FieldMiddlewareCompiler` folds the global, type-level and field-level middleware lists right-to-left into **one `FieldDelegate` per field at schema-build time** ([`FieldMiddlewareCompiler.cs`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/HotChocolate/Core/src/Types/Types/Helpers/FieldMiddlewareCompiler.cs)). (b) A pure-sync lane for trivial getters. In Dart, codegen knows statically that a field is a plain getter or a non-`async` method returning `T`, so it can emit `PureResolver<P, T>` instead of a `FutureOr` resolver.
- **The compiled operation.** `ISelection` is documented as *"the result of compiling and merging field selections"* ([`ISelection.cs`](https://github.com/ChilliCream/graphql-platform/blob/81f8fbd12495f3bbca57a48760824399e1e6f5d6/src/HotChocolate/Core/src/Execution.Operation.Abstractions/ISelection.cs)). ## 11. Scala: Caliban

Pinned: [`ghostdogpr/caliban@b5011d2`](https://github.com/ghostdogpr/caliban/commit/b5011d272e3d47815f3f93b951e0fbabbe2f278f) (series/3.x). Docs: <https://ghostdogpr.github.io/caliban/>.

- **A typeclass is the schema.** `abstract class Schema[-R, T] { def toType(isInput, isSubscription): __Type; def resolve(value: T): Step[R] }` ([`Schema.scala#L39`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/schema/Schema.scala#L39)). One value describes both the GraphQL type *and* how to turn a `T` into a resolution `Step`. Instances for `Option` (nullable), `List` and effects are given ([`#L380-L403`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/schema/Schema.scala#L380), effects [`#L553`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/schema/Schema.scala#L553)). ✅ **Take this exact pairing as the shape of generated code.** For each Dart class the generator emits a `const` descriptor holding the GraphQL type definition plus a typed resolve table. That keeps "schema" and "resolution" from ever drifting apart.
- **Compile-time derivation.** Scala 3 `inline def derived` over `Mirror.SumOf`/`Mirror.ProductOf` ([`SchemaDerivation.scala#L99`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala-3/caliban/schema/SchemaDerivation.scala#L99)), with Magnolia on Scala 2. It offers auto and semi-auto modes (explicit `derives Schema.SemiAuto`). ⚠️ Dart has no `Mirror`, so `build_runner` is the analogue. Semi-auto (opt in per type) fits Dart better: one annotation per class, no global implicit derivation.
- **The sealed-trait mapping is the best rule found anywhere** ([`SumSchema.scala#L11-L60`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala-3/caliban/schema/SumSchema.scala#L33-L39)):
  - a sealed trait whose cases all have no fields (`isEnum = subTypes.forall(… allFields.isEmpty …)`) becomes an **ENUM**;
  - otherwise it becomes a **UNION**; `@GQLUnion` forces a union explicitly;
  - with `@GQLInterface` it becomes an **INTERFACE** (common fields are lifted).

  ✅✅ **Take for Dart.** A plain `enum` maps to a GraphQL ENUM. A `sealed class` with `final class` subtypes maps to a UNION by default, or to an INTERFACE with `@GraphQLInterface()`, whose fields are the sealed base's abstract getters. `__resolveType` becomes a generated exhaustive `switch` with no runtime `is` chains to maintain.
- **Execution through `Step` plus ZQuery.** Resolution produces a `Step` tree, and effectful fields become `QueryStep(ZQuery)` ([`Step.scala#L13-L19`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/schema/Step.scala#L13-L19), [`Schema.scala#L582`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/schema/Schema.scala#L582)). [zio-query](https://github.com/zio/zio-query) batches, pipelines and de-duplicates automatically, because `ZQuery` is a *lazy description* that the executor inspects before running ([`ZQuery.scala#L28-L38`](https://github.com/zio/zio-query/blob/d432dd49672e4a0c9c996691efac0585c6d6afa6/zio-query/shared/src/main/scala/zio/query/ZQuery.scala#L28-L38), `DataSource` [`#L22-L60`](https://github.com/zio/zio-query/blob/d432dd49672e4a0c9c996691efac0585c6d6afa6/zio-query/shared/src/main/scala/zio/query/DataSource.scala#L22-L60)). ❌ The mechanism: a Dart `Future` is *eager*, already running when you hold it, so the executor cannot inspect and batch it. ✅ The goal (batching and de-duplication with no manual wiring) is reachable with a DataLoader that dispatches at the end of the microtask turn (§12, §19.5).
- **Parser.** It uses fastparse, a combinator library ([`Parser.scala`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/core/src/main/scala/caliban/parsing/Parser.scala), dependency at [`build.sbt#L207`](https://github.com/ghostdogpr/caliban/blob/b5011d272e3d47815f3f93b951e0fbabbe2f278f/build.sbt#L207)). ⚠️ This is the outlier among mature implementations. Combinators are not a fit for a Dart hot path or for error recovery.
- **Testing.** It has its own suites plus a federation-compatibility module. No graphql-js fixture port was found.

## 12. Scala: Sangria

Pinned: [`sangria-graphql/sangria@89b7284`](https://github.com/sangria-graphql/sangria/commit/89b7284acfe997c547178304d2133f767ac55e65) (main). Docs: <https://sangria-graphql.github.io/learn/>.

- **The DSL is primary; macros are optional.** `ObjectType("Product", fields[Ctx, Product](Field("name", StringType, resolve = _.value.name)))` is typed by `Ctx` and parent. `deriveObjectType[Ctx, Product]()` is an optional macro shortcut ([learn](https://sangria-graphql.github.io/learn/)). ✅ This supports §19.3: a typed DSL as the *runtime* representation, with codegen as one way of producing it.
- **Deferred resolution on an eager engine.** Sangria is built on Scala `Future` (eager, like Dart's). Its batching is explicit: a resolver returns a `DeferredValue`/`Fetcher` reference, and the executor collects every deferred value at the current level and passes them to a `DeferredResolver` in one batch ([`Fetcher` docs](https://sangria-graphql.github.io/learn/#deferred-value-resolution), [issue #280](https://github.com/sangria-graphql/sangria/issues/280)). ✅ **For Dart this is a closer model than ZQuery.** It shows that a level-synchronous batch point works on eager futures, which is the theory behind §19.5's microtask-dispatched loader.
- **Validation performance** contributed back upstream. Sangria's faster `OverlappingFieldsCanBeMerged` algorithm is the subject of graphql-js [#2185](https://github.com/graphql/graphql-js/issues/2185) (§2.4). ✅
- **Status.** It is still maintained (e.g. [PR #1349](https://github.com/sangria-graphql/sangria/pull/1349) "Speed up query execution/validation/parsing", merged 2026-10-13), though much of the recent history is dependency bumps.

## 13. TypeScript: Pothos (code-first typed builder): deep study

Pinned: [`hayes/pothos@4c8bc28`](https://github.com/hayes/pothos/commit/4c8bc28d0402c4054821c9419d51cf691ba6414d) (main). Docs: <https://pothos-graphql.dev/>, design notes at <https://v4.pothos-graphql.dev/docs/design>.

Pothos describes itself as *"a plugin based GraphQL schema builder for typescript … Pothos does not depend on code-generation or experimental decorators for type-safety."* This makes it the strongest argument for a builder-only Dart design, so it is worth knowing exactly **how** it achieves type safety.

**Correction to a common belief: the builder's type parameter does not grow.** `class SchemaBuilder<Types extends SchemaTypes>` ([`builder.ts#L75`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/builder.ts#L75)) is created *once* with a fixed `Types` bundle: `Context`, `Root`, `Scalars`, `DefaultFieldNullability` and lookup maps `Objects`/`Inputs`/`Interfaces` for name-based references ([`schema-types.ts#L4-L35`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/types/schema-types.ts#L4-L35)). Per-type information travels **through values**, as the design doc puts it: *"Every builder method for creating a type or a field returns a Ref object."* Concretely:
- `ObjectRef<Types, T, P>` carries phantom properties `[outputShapeKey]!: T` and `[parentShapeKey]!: P` that hold nothing at runtime ([`refs/object.ts#L20-L35`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/refs/object.ts#L20-L35)).
- The **conditional types** `OutputShape<Types, T>` and `ParentShape<Types, T>` ([`type-params.ts#L14-L37`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/types/type-params.ts#L14-L37)) branch on what `T` is: a branded Ref, a class constructor (`infer` its instance type), a string key into `Types['Objects']`, or an enum object.
- `builder.objectType(param, options, fields)` ([`builder.ts#L150-L203`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/builder.ts#L150-L203)) derives `ParentShape<Types, Param>` per call and passes an `ObjectFieldBuilder<Types, Shape>` into `fields`. That is why `t.exposeString('name')` type-checks only if `Shape` has a `name: string`.

**What carries over to Dart and what does not:**

| Pothos mechanism | Dart 3 | Verdict |
|---|---|---|
| A fixed `SchemaBuilder<Types>` holding the context type and so on | `class SchemaBuilder<Ctx>` | ✅ |
| A phantom-typed `Ref<T>` returned by every definition | `final class ObjectRef<T> { … }`. The type parameter is reified, so it is not even phantom | ✅ |
| A typed field builder per parent: `t.string('x', resolve: (parent) => …)` | `ObjectBuilder<Ctx, P>` with `field<R>(String name, OutputRef<R> type, FutureOr<R> Function(P, Ctx) resolve)`. Inference works | ✅ |
| `t.exposeString('name')`, which checks by **string key** that `P` has `name: string` | No keyed member types and no key paths. The closest is `t.expose('name', (p) => p.name)` | ❌ needs a closure per field |
| One method accepting a Ref, a class or a string, with a different shape inferred for each | No conditional types, no `infer`, no structural typing | ❌ |
| Typed **argument objects** from a literal `args: { id: t.arg.id({required: true}) }` | Records are positional or named but **cannot be built from a runtime map type-safely** without generated code | ❌ args lose their static type, or need codegen |
| Nullability rules (`DefaultFieldNullability`, `nullable: true` → `T \| null`) | `R` vs `R?` follows from the resolver's return type, but linking it to the declared `OutputRef<R>` takes a second, nullable-wrapper `Ref` | ⚠️ |

**Plugins are declaration merging plus prototype patching.** A plugin extends the type surface by merging into `declare global { namespace PothosSchemaTypes { interface SchemaBuilder<Types> {…} } }` ([core `global/classes.ts#L29-L106`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/core/src/types/global/classes.ts#L29-L106); dataloader plugin [`global-types.ts#L34-L61`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/plugin-dataloader/src/global-types.ts#L34-L61)). It then implements the new method by assigning onto `SchemaBuilder.prototype` ([`plugin-dataloader/src/schema-builder.ts#L23-L37`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/plugin-dataloader/src/schema-builder.ts#L23-L37)). ❌ Dart has neither open interfaces nor monkey-patching. ⚠️ The closest Dart tool is **extension methods** on `ObjectBuilder<Ctx, P>` from a plugin package, e.g. `extension DataloaderFields<C, P> on ObjectBuilder<C, P> { void loadable<K, V>(…) }`. Extensions can add *API surface* but cannot add *state* or hook into build steps, so plugins still need an explicit registration list. The `loadableObject` feature itself ([`plugin-dataloader/src/index.ts#L22-L39`](https://github.com/hayes/pothos/blob/4c8bc28d0402c4054821c9419d51cf691ba6414d/packages/plugin-dataloader/src/index.ts#L22-L39), whose `wrapResolve` turns a field that returns a bare key into `loader.load(key)`) ✅ is a good ergonomic target.

**Verdict.** A Pothos-style Dart builder can be *fully typed for parent, context and return value*. It cannot also be terse (no key paths) or type its *arguments* without codegen. It is the right **runtime representation** and escape hatch, but not the best primary authoring surface (§19.3).

## 14. TypeScript: Grats (static analysis of plain code)

Pinned: [`captbaritone/grats@5a6b449`](https://github.com/captbaritone/grats/commit/5a6b449e7f56e3d293190a37760f117d3baf835d) (main). Docs: <https://grats.capt.dev/>.

- **Approach.** You annotate ordinary TS declarations with JSDoc tags (`/** @gqlType */ class User { /** @gqlField */ name: string; … }`), and a CLI emits `schema.graphql` plus an executable `schema.ts` ([README](https://github.com/captbaritone/grats/blob/5a6b449e7f56e3d293190a37760f117d3baf835d/README.md)). At runtime, *"the generated TypeScript code is just a module that exports a function which builds your `GraphQLSchema`… It does not use any Grats code at runtime."*
- **Implementation (corrected).** Grats is now **Rust on oxc**, not the TypeScript compiler API: *"Grats is written in Rust … It parses your TypeScript code with oxc … Grats does not run the TypeScript compiler"*. It resolves type names through oxc's semantic analysis ([`how-grats-works.md#L9-L21`](https://github.com/captbaritone/grats/blob/5a6b449e7f56e3d293190a37760f117d3baf835d/website/docs/06-faq/03-how-grats-works.md#L9-L21)). It emits code by building an AST rather than concatenating strings (L39), and reports schema errors **at the original TS source spans**.
- **Structural vs nominal.** Because TS is structural and GraphQL nominal, Grats requires every GraphQL-typed annotation to name a declaration and rejects inline literal types ([structural-vs-nominal FAQ](https://github.com/captbaritone/grats/blob/5a6b449e7f56e3d293190a37760f117d3baf835d/website/docs/06-faq/04-structural-vs-nominal-typing.md)). ✅ Dart is nominal, so this problem disappears: a class *is* its GraphQL type.
- **Production use.** The author is a Meta engineer on Relay, and the README credits Meta's Hack GraphQL server as inspiration. A specific "used at Meta/Tumblr" claim **could not be verified** in the repo.
- ✅✅ **Take: Grats is the TypeScript proof of the Dart plan.** Plain classes, a build-time analyzer reading annotations and resolved types, generated schema plus resolver glue, zero runtime library cost, and diagnostics pointing at user source. `package:analyzer` provides *resolved* element types, which Grats deliberately does without, so a Dart generator can be stricter (e.g. check that an `@Field` getter's `int` matches a declared `Int!`).

## 15. TypeScript: TypeGraphQL and Nexus (brief)

**TypeGraphQL** ([`MichalLytek/type-graphql@77a79f2`](https://github.com/MichalLytek/type-graphql/commit/77a79f2e13a39185a8669087497dcf626bb2f285)) builds schemas from `@ObjectType()`/`@Field()` decorators. It reads TypeScript's emitted `design:type`/`design:returntype`/`design:paramtypes` metadata through `reflect-metadata` ([`findType.ts`](https://github.com/MichalLytek/type-graphql/blob/77a79f2e13a39185a8669087497dcf626bb2f285/src/helpers/findType.ts), [`Field.ts`](https://github.com/MichalLytek/type-graphql/blob/77a79f2e13a39185a8669087497dcf626bb2f285/src/decorators/Field.ts)) and throws `ReflectMetadataMissingError` without the polyfill ([source](https://github.com/MichalLytek/type-graphql/blob/77a79f2e13a39185a8669087497dcf626bb2f285/src/errors/ReflectMetadataMissingError.ts)). That metadata loses generics, nullability and unions, hence `@Field(() => [User], { nullable: true })` thunks everywhere. ❌ Runtime reflection is a non-starter in AOT Dart, and the thunks show what happens when the type source is lossy. ✅ The annotate-a-class ergonomics are the target, reached at build time.

**Nexus** ([`graphql-nexus/nexus@9e5c27c`](https://github.com/graphql-nexus/nexus/commit/9e5c27c50901b038e276c8a2ec4bb5ace1415580)) offers a code-first `objectType({ name, definition(t) { t.string(…) } })` plus a **round-trip typegen**. `makeSchema({ outputs: { typegen } })` writes a `.d.ts` whose `declare global { interface NexusGen extends NexusGenTypes {} }` ([`typegenPrinter.ts#L1107-L1110`](https://github.com/graphql-nexus/nexus/blob/9e5c27c50901b038e276c8a2ec4bb5ace1415580/src/typegenPrinter.ts#L1107-L1110)) merges into the empty interfaces declared in core ([`typegenTypeHelpers.ts`](https://github.com/graphql-nexus/nexus/blob/9e5c27c50901b038e276c8a2ec4bb5ace1415580/src/typegenTypeHelpers.ts)). The resolver types therefore become precise only *after* one run. ❌ Global merging has no Dart equivalent. ⚠️ The two-phase idea is the same as schema-first codegen, where the generated file is imported normally. **Status:** the last commit on `main` is 2023-03-16, with 254 open issues. It is not archived but is effectively unmaintained, so treat it as reference only.

- **Yoga: four layers.** `Plugin = EnvelopPlugin & ServerAdapterPlugin & { onYogaInit, onRequestParse, onParams, onExecutionResult, onResultProcess }` ([`plugins/types.ts`](https://github.com/graphql-hive/graphql-yoga/blob/9d29d6e9a9fdf353082fa036f51255ae727199af/packages/graphql-yoga/src/plugins/types.ts)). So the stack is **engine → envelop phase plugins → generic Request/Response adapter → GraphQL-over-HTTP binding**, with `@defer`/`@stream`, SSE and subscriptions as separate packages. ✅✅ **Take this layering for the Dart transports**, with `shelf` (or a `Request → Response` function) as the generic adapter.
- **APQ** ([`plugins/apq/src/index.ts`](https://github.com/graphql-hive/graphql-yoga/blob/9d29d6e9a9fdf353082fa036f51255ae727199af/packages/plugins/apq/src/index.ts), 137 lines). It runs in `onParams` and reads `extensions.persistedQuery { version: 1, sha256Hash }`, hashing with SHA-256. Errors are `PersistedQueryNotFound` (HTTP 404) and `PersistedQueryMismatch` (400). The store is a `{get, set}` interface (default LRU `max: 1000`, `ttl: 36_000`). ✅ Docs distinguish APQ ([link](https://the-guild.dev/graphql/yoga-server/docs/features/automatic-persisted-queries)) from trusted documents ([link](https://the-guild.dev/graphql/yoga-server/docs/features/persisted-operations)). Ship both.
- **@graphql-tools** `makeExecutableSchema({ typeDefs, resolvers })` ([source](https://github.com/ardatan/graphql-tools/blob/9e251e455948b9ec4c74a72dbf49b512ddae19d2/packages/schema/src/makeExecutableSchema.ts)) types `resolvers?: IResolvers<any, TContext>` ([`types.ts`](https://github.com/ardatan/graphql-tools/blob/9e251e455948b9ec4c74a72dbf49b512ddae19d2/packages/schema/src/types.ts)). The resolver map is `any`-typed, and real typing comes only from `@graphql-codegen/typescript-resolvers`. ❌ An untyped resolver map as the primary API. ✅ More evidence that schema-first needs codegen to be typed (§17). Stitching and delegation have moved to Hive Gateway/Mesh.

## 17. Go: gqlgen (schema-first, generated typed resolver interfaces)

Pinned: [`99designs/gqlgen@72b25c1`](https://github.com/99designs/gqlgen/commit/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9) (master). Docs: <https://gqlgen.com/>.

- **Pipeline.** The CLI is the repo-root `main.go` (`init`/`generate`), `go run github.com/99designs/gqlgen generate` or `go tool gqlgen` ([`main.go#L166-L194`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/main.go#L166-L194)). `api.Generate` runs a plugin pipeline: `modelgen` (if configured), `resolvergen`, and optionally federation ([`api/generate.go#L51-L90`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/api/generate.go#L51-L90)). SDL is parsed with `vektah/gqlparser`.
- **Output shape, which is config-driven** ([`config.md#L15-L61`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/docs/content/config.md#L15-L61)):
  - an **exec** file (`generated.go`, *DO NOT EDIT*) holds both the resolver interfaces *and* the execution glue;
  - an optional **models** file (`models_gen.go`) has structs for types not bound to existing ones;
  - **resolver stubs**, one file per schema file (`follow-schema` layout), are regenerated with existing method bodies *copied through*;
  - a root `resolver.go` that *"wont get regenerated"*.
- **The contract.** For `schema { query: MyQuery, mutation: MyMutation }` it generates:

  ```go
  type ResolverRoot interface { MyMutation() MyMutationResolver; MyQuery() MyQueryResolver }
  type MyQueryResolver interface {
      Todo(ctx context.Context, id int) (*Todo, error)
      Todos(ctx context.Context) ([]*Todo, error)
  }
  ```

  ([`_examples/todo/generated.go#L30-L71`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/generated.go#L30-L71)). The Go compiler then checks the hand-written implementation. ✅✅ **The Dart analogue is a generated `abstract class QueryResolver { FutureOr<List<Todo>> todos(Ctx ctx); }`.** The analyzer enforces names, argument types, return types *and* nullability.
- **Obligations only where needed.** A field gets a resolver method **only if it cannot auto-bind** to a field, method or tag on the bound Go type, or if it is forced. In `_examples/config`, only `Todo.id` (marked `@goField(forceResolver: true)`) produces `TodoResolver.ID(ctx, obj *Todo)`. `databaseId`/`done` bind directly, and `text` binds to the renamed field `Description` through config ([`todo.graphql#L1-L9`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/config/todo.graphql#L1-L9), [`generated.go#L29-L85`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/config/generated.go#L29-L85)). The binding order is struct field → method → struct tag → explicit config ([resolvers reference](https://gqlgen.com/reference/resolvers/)). ✅✅ **Take nearly verbatim.** ⚠️ Improvement for Dart: when a bound class's member *exists but has the wrong type or nullability*, raise a **build error** instead of silently adding a resolver obligation. The analyzer has the resolved `DartType`, so this is cheap.
- **Model binding.** `models: Todo: model: …/todo.Todo` binds to a hand-written struct, and `autobind:` scans whole packages ([`_examples/todo/gqlgen.yml`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/gqlgen.yml)). Unbound types are generated. ✅ Support both: generated classes by default, and a `build.yaml`/directive mapping to existing Dart classes.
- **Nullability is a convention in Go.** `[String]` → `[]*string`, `[String!]!` → `[]string`, with null vs non-null list expressed only through `nil` ([`slices.graphql`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/codegen/testserver/singlefile/slices.graphql) → [`models-gen.go#L253-L258`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/codegen/testserver/singlefile/models-gen.go#L253-L258)). The runtime therefore needs an `InvalidNullError` check to catch a `nil` returned for a non-null field ([`graphql/invalid_null.go`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/graphql/invalid_null.go)). ✅ Dart's sound null safety makes *"resolver returned null for a non-null field"* a compile error for typed resolvers. Null **bubbling** is still needed because resolvers throw, but the defensive null check covers only untyped/dynamic resolvers.
- **Directives as typed middleware slots.** `type DirectiveRoot struct { HasRole func(ctx, obj any, next graphql.Resolver, role Role) (any, error) }` ([`generated.go#L35-L38`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/generated.go#L35-L38)). You implement a slot once, and the generated code wires it into every annotated field with typed, pre-coerced arguments ([wiring `#L982-L1004`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/generated.go#L982-L1004), [directives docs](https://gqlgen.com/reference/directives/)). Codegen-only directives (`@goField`, `@goModel`) are hidden from runtime introspection with `skip_runtime`. ✅✅ In Dart, generate a `Directives` class with one typed `FieldMiddleware` slot per schema directive, compiled into the per-field chain (§10).
- **Execution.** Code is **generated per field**: direct struct access (`obj.ID`) and type-specific marshalers (`marshalNString2string`). The generated exec file contains **no reflection**; a little reflection remains in hand-written runtime helpers for legacy input coercion and as a cache key ([`graphql/input.go`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/graphql/input.go)). `FieldSet.Dispatch` has a **fast path**: one delayed field runs inline, and with more than one, the first runs on the current goroutine and the others get goroutines ([`graphql/fieldset.go#L126-L150`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/graphql/fieldset.go#L126-L150)). Root mutation fields execute serially inline, while root query fields are scheduled concurrently ([`generated.go#L2213-L2316`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/todo/generated.go#L2213-L2316)). ✅ The Dart analogue is to avoid `Future.wait` unless at least two siblings actually returned a `Future`.
- **DataLoader.** It is not in core. The docs recommend [`vikstrous/dataloadgen`](https://gqlgen.com/reference/dataloaders/) with middleware-injected loaders. gqlgen has also added **batch resolvers** (`@goField(batch: true)`), where codegen hands your resolver *all sibling parents at once* ([resolvers reference § Batch resolvers](https://gqlgen.com/reference/resolvers/), [`_examples/batchresolver`](https://github.com/99designs/gqlgen/tree/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/_examples/batchresolver)). ⚠️ This is a good v2 feature for Dart: `FutureOr<List<R>> field(List<P> parents)`, which removes N+1 with no loader at all.
- **Introspection** goes through the same generated field functions, over a wrapped schema. It is **opt-in** middleware (`srv.Use(extension.Introspection{})`) and can be disabled per request ([introspection docs](https://gqlgen.com/reference/introspection/)). ✅ Disable it by default in production profiles.
- **Testing and performance.** It uses an internal `codegen/testserver` plus introspection round-trip checks ([TESTING.md](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/TESTING.md)). No published throughput numbers exist, but **CI gates merges on allocation regressions** (`B/op`, `allocs/op`) ([`.github/workflows/benchmarks.yaml`](https://github.com/99designs/gqlgen/blob/72b25c16e9e2f03238f3a581b05a46f94dc1c7b9/.github/workflows/benchmarks.yaml)). ✅ Track allocations per field in CI from day one.
- ❌ **Avoid the stub-merging regeneration.** Copying hand-written bodies forward into regenerated files is AST-diffing magic, and `build_runner` should never rewrite user files. In Dart the user `extends` the generated abstract class in their own file, and inheritance does the "preservation".

## 18. Haskell: Morpheus GraphQL (brief — confirms a cross-language consensus)

Pinned: [`morpheusgraphql/morpheus-graphql@db93df2`](https://github.com/morpheusgraphql/morpheus-graphql/commit/db93df213fd2716dbd8aafb81a07e3a8a6ea5967) (main, 414 stars, pushed 2026-06-15). Docs: <https://morpheusgraphql.com/>. `higherkindness/mu-haskell` was checked and is **archived** (last push 2024-08-01) — out of scope, not covered further.

Morpheus's own pitch: *"Morpheus will convert your Haskell types to a GraphQL schema and all your resolvers are just native Haskell functions"* ([README](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/README.md)). Two front doors reach one derived representation:
- **Type-first.** A plain record/ADT with `deriving (Generic, GQLType)` is enough: `GQLType` is a class with an associated type family `type KIND a :: DerivingKind` defaulting to `TYPE` ([`GQLType.hs#L222-224`](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/morpheus-graphql-server/src/Data/Morpheus/Server/Types/GQLType.hs#L222-L224)), with `instance GQLType (Maybe a) where type KIND (Maybe a) = WRAPPER` hard-wiring nullability to `Maybe` ([`GQLType.hs#L283-284`](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/morpheus-graphql-server/src/Data/Morpheus/Server/Types/GQLType.hs#L283-L284)) — `Text`/`Maybe Text` map to `String!`/`String` with zero separate annotation, the same rule independently found in Rust, Kotlin, Swift and Scala (§5, §7, §9, §11). This is compile-time generic-deriving (GHC `Generic`/`DeriveAnyClass`), not runtime reflection — closer in spirit to a Rust derive macro than to graphql-kotlin's `kotlin-reflect` (§7).
- **Schema-first.** A single Template Haskell call, `importGQLDocument "schema.gql"`, parses an SDL file and generates the matching Haskell record/sum types at compile time for the resolver implementation to reference ([README, "with GraphQL syntax"](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/README.md)) — the mirror image of type-first, landing in the identical `GQLType`-derived representation either way.

`RootResolver m e query mutation subscription` plus an `Undefined` sentinel for unused root operations — `rootResolver :: RootResolver IO () Query Undefined Undefined` ([README](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/README.md), re-exported from [`Types.hs`](https://github.com/morpheusgraphql/morpheus-graphql/blob/db93df213fd2716dbd8aafb81a07e3a8a6ea5967/morpheus-graphql/src/Data/Morpheus/Types.hs)) — proves "this API has no mutations" in the type signature itself, instead of a runtime null/empty-type check.

Execution rides on Haskell's laziness: every field is uniformly monadic (`a -> m b`), and there is no sync/async split to design around, because GHC's call-by-need makes the "nothing to await" case free at the runtime-representation level. That is a genuine, simpler alternative — but it depends on laziness Dart does not have; it does **not** contradict this doc's `FutureOr` fast-path recommendation (§2.5, §0 pattern 4), it just shows the dichotomy is run-time-model-specific rather than universal.

**Verdict.** Morpheus adds no new idea beyond what five other ecosystems already established — it is simply the next independent confirmation that (a) nullability should come from the host language's own type (`Maybe`/`Option`/`T?`, pattern 9) and (b) closed sum types are the right representation for GraphQL unions/enums (pattern 10; Morpheus's sum-type handling is structurally the same derivation path as its records, just dispatched through a different `DerivingKind`). Its one distinctive, worth-keeping contribution is the **dual type-first/schema-first front door sharing one derived core**, which independently matches this doc's own §19 recommendation (one runtime IR behind two generator front ends) — a cross-check, not a new top-N entry.

Dart tags: ✅ take (already covered by pattern 9/10, reinforced here) — derive nullability and union/enum shape from Dart's own `?`/`sealed class`. ✅ take (small, novel) — a generated `NoMutation`/`NoSubscription` marker type recognized by the schema builder and omitted from the emitted SDL, rather than a nullable `mutationType` runtime check. ❌ avoid — relying on laziness for a "free" synchronous path; Dart needs the explicit `FutureOr` discipline used elsewhere in this doc (§2.5, §0 pattern 4).

## 19. Synthesis: recommended architecture for Dart

The implementations above agree on far more than their marketing suggests. All three serious front ends (graphql-js, apollo-rs, Apollo Kotlin) use hand-written recursive-descent parsers. Every typed server derives `!` from the host language's nullability (async-graphql, juniper, graphql-kotlin, Graphiti, Caliban). Every high-performance executor has a sync or no-allocation fast path (graphql-js, Hot Chocolate, gqlgen), and the one that does not is still paying for it (graphql-java). The disagreements are about **where types come from**, and that is where Dart's constraints (no runtime reflection, no conditional types, `build_runner` available) decide the answer.

### 19.1 Layering

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ transports (separate packages)                                               │
│   graphql_shelf: GraphQL-over-HTTP (GET/POST, application/graphql-response+  │
│     json), multipart incremental, SSE (graphql-sse), WebSocket               │
│     (graphql-transport-ws); a Request→Response core, adapters per server     │  ← yoga 4-layer stack (§16)
├──────────────────────────────────────────────────────────────────────────────┤
│ graphql_server: request pipeline + Extension chain (next-chained phases)     │  ← async-graphql Extension (§5),
│   built-ins: depth/cost limits, APQ + trusted documents, response cache,     │     envelop phases (§16)
│   tracing (OpenTelemetry), introspection toggle, error masking               │
├──────────────────────────────────────────────────────────────────────────────┤
│ graphql_execution: plan compiler (cached, single-flight) → FutureOr executor │  ← Hot Chocolate (§10),
│   PureResolver lane, per-field middleware folded at build, serial mutations, │     graphql-js fast path (§2.5),
│   null bubbling / onError, Stream subscriptions, incremental (opt-in)        │     gqlgen dispatch (§17)
│ graphql_dataloader: Batch + Grouped loaders, request-scoped, auto-dispatch   │  ← GreenDonut (§10), Sangria (§12)
├──────────────────────────────────────────────────────────────────────────────┤
│ graphql_validation: spec rules as visitors fused by ParallelVisitor          │  ← graphql-js visitInParallel (§2.4)
│   + TypeInfo; returns ValidDocument (typestate) bound to a ValidSchema       │  ← apollo-rs Valid<T> (§4.3)
├──────────────────────────────────────────────────────────────────────────────┤
│ graphql_schema: immutable type-system model (LinkedHashMap, sealed TypeDef), │  ← apollo-compiler Schema (§4.2)
│   SDL ⇄ model, schema validation → ValidSchema, introspection as types,      │  ← graphql-js introspection (§2.7)
│   typed scalars, builder API (typed, the runtime IR all front-ends target)   │  ← Pothos/Sangria DSL (§13, §12)
├──────────────────────────────────────────────────────────────────────────────┤
│ graphql_language: Source, codeUnitAt lexer, recursive-descent parser,        │  ← apollo-parser (§4.1),
│   error-resilient (doc + diagnostics), byte-offset spans, sealed AST,        │     graphql-js parser (§2.1)
│   printer, Visitor/ParallelVisitor; later: lossless CST for fmt/LSP          │
└──────────────────────────────────────────────────────────────────────────────┘
  graphql_codegen (build_runner, dev_dependency): two front-ends, one output
    (a) annotations on Dart classes  → descriptors + glue + schema.graphql
    (b) .graphql SDL                 → models + abstract resolver classes + descriptors
```

Each layer depends only on the layers below it. `graphql_language` has **zero dependencies**, so it is reusable by the client codegen (doc 04), a formatter and an LSP.

### 19.2 Per-layer decisions

| Layer | Decision | Taken from | Avoid |
|---|---|---|---|
| **Lexer** | Scan `String.codeUnitAt` with an `int` cursor. Tokens are `(kind, start, end)`, value slices are taken lazily, and comments are kept as trivia tokens, not discarded. The lexer never throws and emits `error` tokens instead. | apollo-parser lexer *"never fails"* (§4.1); graphql-js readers (§2.1) | graphql-js dropping comments (#2241) |
| **Parser** | Hand-written recursive descent, one method per production. **Error-resilient**: returns `ParseResult(Document doc, List<Diagnostic> errors)`, inserts error/missing nodes and resynchronises at definition and selection boundaries. A strict `parse()` that throws is a thin wrapper. | apollo-parser `err_and_pop` + `SyntaxTree{errors}` (§4.1) | graphql-js throw-on-first-error (#1426) |
| **Spans** | `int start, end` byte (code-unit) offsets in every node. Line/column comes from a lazily built line-start table on `Source`. | apollo-compiler `SourceSpan` + lazy `LineColumn` (§4.1) | regex re-scan per lookup (graphql-js `getLocation`) |
| **AST** | `sealed class Node` hierarchy of `final class`es with `const` constructors and immutable `List`s. The executable and type-system halves are separate sealed families. No arena, no interning in v1. A **lossless CST** (trivia-preserving) is a *later* opt-in package for formatter/LSP; it lowers to the same AST. | Apollo Kotlin `sealed interface GQLNode` (§8); apollo-rs CST→AST lowering (§4.2) | salsa-style incremental DB in core (apollo-rs removed it for a 1.2–2× speedup, §4.2) |
| **Schema model** | Immutable `Schema` with `LinkedHashMap<String, TypeDefinition>` (insertion order = SDL order), `sealed class TypeDefinition` (Scalar/Object/Interface/Union/Enum/InputObject). `Schema.validate()` returns `ValidationResult<ValidSchema>`. **`ValidSchema` is a `final class` with a private constructor** and an explicit `ValidSchema.assumeValid()`. | apollo-compiler `Schema` + `Valid<T>` (§4.2–4.3) | extension-type typestate (forgeable); graphql-java builders (§3) |
| **Validation** | One rule = one class implementing `enter/leave(Node)` with a `switch` on the sealed node type. **All rules run in a single walk** via `ParallelVisitor` plus `TypeInfo` tracking, with per-rule skip/break. The document becomes `ValidDocument` only when bound to a `ValidSchema`. Port graphql-js's rule tests. Use the Sangria algorithm for `OverlappingFieldsCanBeMerged`. Depth, cost and no-introspection are ordinary pluggable rules. | graphql-js `visitInParallel` (§2.4); HC per-rule visitors (§10); async-graphql limits-at-validation (§5) | apollo-rs's fixed direct passes (good for a compiler; not user-extensible, §4.4); graphql-js #2185 algorithm |
| **Plan** | `ValidDocument + operationName` compiles to an **`OperationPlan`**: per (object type, selection set) a list of merged `PlannedField`s (response key, field def, coerced *literal* args, child plan, defer usage). Cached in an LRU keyed by `(documentHash, operationName)`, with single-flight compilation. Variables are applied at execution time. | HC compiled `ISelection` + `OperationCacheMiddleware` (§10); graphql-js v17 `buildExecutionPlan` (§2.6) | per-request `collectFields` (graphql-js #4008) |
| **Executor** | Resolvers return **`FutureOr<T>`**. The engine checks `is Future` at each level and only then allocates (`containsFuture` like graphql-js). Fields statically known to be sync getters use a **`PureResolver` lane** with no middleware context and no `FutureOr` checks. `Future.wait` runs only when ≥2 siblings are actually async. Mutations are serial and queries interleaved. Spec null bubbling (`completeValue` + `handleFieldError`), with the error-behavior mode (`PROPAGATE`/`NULL`/`HALT`, doc 01 §9) as a parameter. Subscriptions are `Stream` → `asyncMap(execute)`. `@defer`/`@stream` go through a separate `executeIncrementally` that returns `Stream<IncrementalPayload>` and is off unless the schema opts in. | graphql-js (§2.5–2.6); HC `PureFieldDelegate`/`ValueTask` (§10); gqlgen `Dispatch` (§17); async-graphql `parallel` flag (§5) | `CompletableFuture`/`Future` per field (graphql-java #3331); an `async` wrapper on every field; sync-first + async retrofit (juniper, §6) |
| **Field middleware** | `typedef FieldMiddleware = FieldResolver Function(FieldResolver next)`, composed **once per field at schema build** (global → type → field → directive slots). An empty chain means the raw resolver is called directly. | HC `FieldMiddlewareCompiler` (§10); gqlgen `DirectiveRoot` slots (§17) | envelop `on-resolve` monkey-patching (§16) |
| **DataLoader** | Separate package. `BatchLoader<K,V>` (`Future<Map<K,V>> load(List<K>)`) and `GroupedLoader<K,V>` (`Future<Map<K,List<V>>>`). Loaders are request-scoped (created lazily from the request context), with per-request de-dup/cache and automatic dispatch after the current microtask burst; the executor can also force a flush at level boundaries. A v2 option is generated **batch resolvers** (`List<P> → List<R>`). | GreenDonut (§10); async-graphql `Loader` (§5); Sangria deferred (§12); gqlgen batch resolvers (§17) | ZQuery-style laziness (impossible with eager `Future`, §11); JVM dispatch instrumentation (§7) |
| **Request pipeline** | `abstract class Extension` with `next`-chained phases: `request`, `parse`, `validate`, `execute`, `subscribe`, plus optional `resolve` (folded into field middleware only when overridden). Context is a typed `ContextBag` (`ctx.get<T>()`) with a generated app-specific facade. | async-graphql `Extension` (§5); envelop `Plugin` phases (§16) | graphql-java's 20-hook `Instrumentation` and its churn (§3) |
| **Introspection** | Ordinary object types whose resolvers read the `ValidSchema`, so the same executor runs them. Can be disabled per request or by default in production. | graphql-js (§2.7); gqlgen opt-in (§17) | special-cased serializer |
| **Transports** | Generic `Request → Response` core, then the GraphQL-over-HTTP binding, then plugins. APQ (`extensions.persistedQuery`, 404/400 errors, pluggable store) and a trusted-documents allowlist are separate plugins. | yoga 4 layers + APQ plugin (§16) | |
| **Conformance** | Port graphql-js `__tests__` (validation per rule, execution); grammar fuzzing (`graphql_smith`-style); CI benchmarks gating on allocations; run the whole suite under `dart compile exe` (AOT sealed-switch bug sdk#56010, doc 05 §6). | graphql-js (§2.8); apollo-smith (§4.5); gqlgen benchgate (§17) | |

### 19.3 How to get full static typing for resolvers: three options compared

The executor needs one thing at runtime: per field, a function `(parent, args, ctx, info) → FutureOr<value>` plus the field's GraphQL type. **What differs is who writes the glue and what checks it.** Each option is shown for the same schema fragment (`type User { name: String!  posts(first: Int = 10): [Post!]! }`).

**A. Schema-first plus generated abstract resolver classes (gqlgen style).** You write `.graphql`, and `build_runner` emits models (or binds to your classes through `build.yaml`) plus one abstract class per type that has non-bindable fields:

```dart
// GENERATED from user.graphql. `User` bound to lib/models/user.dart via build.yaml,
// so `name` auto-binds to `User.name` and creates no obligation.
abstract class UserResolver<C> {
  FutureOr<List<Post>> posts(User parent, C ctx, {required int first});
}
// HAND-WRITTEN
final class AppUserResolver extends UserResolver<AppContext> {
  @override
  Future<List<Post>> posts(User parent, AppContext ctx, {required int first}) =>
      ctx.loaders.postsByAuthor.load(parent.id).then((p) => p.take(first).toList());
}
```

**B. Code-first typed builder with Dart generics (Pothos style), no codegen:**

```dart
final user = b.object<User>('User', (t) => [
  t.field('name', b.string, (u, ctx) => u.name),               // R inferred as String
  t.field('posts', b.list(post), (u, ctx, args) =>             // args: untyped map/accessor
      ctx.loaders.postsByAuthor.load(u.id),
      args: {'first': b.arg(b.int, defaultValue: 10)}),
]);
```

**C. Annotations plus codegen (async-graphql / Grats / HC implementation-first):**

```dart
@GraphQLObject()
final class User {
  const User(this.id, this.name);
  final UserId id;                 // @Ignore()d or exposed as ID! (configurable)
  final String name;               // → name: String!  (plain getter → PureResolver)
  @Field()
  Future<List<Post>> posts(AppContext ctx, {int first = 10}) =>   // → posts(first: Int = 10): [Post!]!
      ctx.loaders.postsByAuthor.load(id).then((p) => p.take(first).toList());
}
// GENERATED (user.g.dart): const descriptor + cast-free glue + contribution to schema.graphql
```

| Criterion | A. Schema-first + abstract classes | B. Typed builder (no codegen) | C. Annotations + codegen |
|---|---|---|---|
| Parent type checked | ✅ | ✅ (`object<User>`) | ✅ (`this`) |
| Result type and nullability checked against GraphQL type | ✅ generated signature | ⚠️ only if refs encode nullability (`b.string` vs `b.string.nullable`) and `R` unifies; easy to get wrong | ✅ *derived from* the Dart type |
| Arguments typed | ✅ named params | ❌ map/accessor (no conditional types; §13) | ✅ named params, defaults included |
| Context typed | ✅ `<C>` | ✅ `SchemaBuilder<Ctx>` | ✅ parameter type |
| Boilerplate | medium (SDL + impl classes) | high (a closure per field, no key paths) | **lowest** (plain fields bind as pure getters) |
| Source of truth | SDL (contract-first, federation-friendly) | Dart code | Dart types, with **`schema.graphql` emitted** for review/diff/client codegen |
| Build step and pre-build IDE state | yes; impl shows errors until generated | **none**; instant feedback | yes; the class itself is valid Dart before the build |
| Dynamic or runtime-assembled schemas | ❌ | ✅ | ❌ |
| Evolving the schema | edit SDL → regen → compiler lists every missing or changed method ✅ | edit code | edit code; SDL diff in CI shows breaking changes |
| Domain/API separation | strong (SDL is the API) | medium | weaker (API shape = domain classes, mitigated with dedicated `@GraphQLObject` DTOs) |
| Prior art | gqlgen, graphql-codegen `typescript-resolvers`, HC schema-first | Pothos, Nexus, Sangria DSL, Graphiti, HC code-first | async-graphql, juniper, Grats, HC implementation-first, Caliban (compile-time), graphql-kotlin (reflection) |

**Recommendation: one runtime IR, two codegen front ends, and the builder as the public escape hatch.** Hot Chocolate shows that this works: three authoring styles lower into one type model (§10).
1. **The runtime IR is the typed builder/descriptor API (B)**: `ObjectTypeDef<P>`, `FieldDef<P, R>`, `OutputRef<R>`. Generated code targets it, and hand-written code can use it for dynamic schemas, tests and edge cases. Keep it public but documented as low-level.
2. **The primary front end is annotations plus `build_runner` (C).** Dart developers already work this way (`json_serializable`, `freezed`). It needs the least boilerplate, gets nullability, arguments and defaults *for free* from the analyzer's resolved types, makes plain getters into `PureResolver`s, and maps `enum` / `sealed class` / `@GraphQLInterface` to ENUM / UNION / INTERFACE using Caliban's rule (§11). Like Grats (§14), it **emits `schema.graphql`** so the client codegen (doc 04) and schema-diff CI have an SDL artifact.
3. **The second front end is schema-first (A)** for contract-first teams and federation subgraphs. It generates models or binds to existing classes (gqlgen's binding order, §17), and generates abstract resolver classes **only for fields that cannot auto-bind**. A bound member with the wrong type is a build error, not a silent resolver obligation. Directives become typed middleware slots.
4. Both generators share the **same emitter** (descriptors plus cast-free glue). Only the *input model* differs: analyzer elements vs. a parsed `ValidSchema`. Use one `source_gen` package, ship `custom_lint` rules alongside it as HC does (§10), and never rewrite user files (unlike gqlgen's stub merging, §17).

### 19.4 Typing details that follow from the choice
- **Nullability.** `T` → `T!` and `T?` → `T`; `List<T>` → `[T!]!`, `List<T?>?` → `[T]`. Typed resolvers therefore *cannot* return null for a non-null field, which removes gqlgen's `InvalidNullError` defence (§17). Null *bubbling* is still required because resolvers throw.
- **Async shapes.** The generator unwraps `Future<T>`/`FutureOr<T>` → `T`, and `Stream<T>` on subscription roots → `T`. It does the same for `FieldResult<T>`, a value plus partial errors and extensions, like graphql-kotlin's `DataFetcherResult` (§7). An `async` method is detected statically and routed to the async lane, while a getter or non-`async` method returning `T` goes to the pure lane.
- **Input objects and arguments.** Each input type becomes a generated `final class` with a `fromCoerced` factory. The *absent vs null* distinction uses `Optional<T?>`-style two-variant wrapping (doc 04 pattern 3) only where the schema needs it (nullable input fields without defaults), and plain `T?` elsewhere.
- **Abstract types.** `sealed class Node` + `final class User extends Node` → INTERFACE/UNION. `resolveType` is a generated exhaustive `switch`, so adding a subtype breaks the build until the schema accounts for it. That is Dart's compile-time answer to the runtime `__resolveType` maps of graphql-js.
- **Typestate at the API boundary.** `execute(ValidSchema schema, ValidDocument doc, {…})` cannot be called with unvalidated input, the guarantee apollo-compiler gives (§4.3). `ValidDocument.validate(doc, schema: validSchema)` is the only constructor apart from `assumeValid` (for persisted, pre-validated documents, e.g. trusted documents loaded at boot).

### 19.5 Pitfalls checklist

| # | Pitfall | Evidence | Mitigation |
|---|---|---|---|
| 1 | A `Future` per field | graphql-java #3331 / PR #3480 / `@DuckTyped` (§3); Dart `async` always allocates ([SDK Calls benchmark](https://dart.googlesource.com/sdk/+/0f15e32ad3551ca492a5a7c62d9182d1e4fd4627/benchmarks/Calls/dart/Calls.dart), doc 05 §6) | `FutureOr` everywhere in the engine, no `async` on hot paths, `containsFuture` aggregation, `PureResolver` lane |
| 2 | Middleware turns every field async | async-graphql always-on `resolve` hook (§5); HC's separate `PureFieldDelegate` (§10) | fold chains at schema build; empty chain = direct call |
| 3 | `Future.wait` for one async child | gqlgen `Dispatch` fast path (§17) | wait only when ≥2 siblings returned a `Future` |
| 4 | Per-request field collection | graphql-js #4008 (up to 50% slower, §2.6) | cached `OperationPlan`, single-flight (§10) |
| 5 | Retrofitting async or incremental delivery | juniper's two traits (§6); graphql-js #4534 revert → #4537 replace → #4545 split (§2.6) | `FutureOr` from day one; plan carries defer usage from day one |
| 6 | Over-engineered incremental core | apollo-rs removed salsa (§4.2) | plain immutable models; caching only at the plan level |
| 7 | Runtime reflection | graphql-kotlin `callBy` (§7), TypeGraphQL `reflect-metadata` (§15) | build-time analyzer codegen only |
| 8 | Instrumentation by monkey-patching / sprawling hook interface | envelop `on-resolve` (§16); graphql-java deprecations and walk-backs (§3) | small `Extension` phase set + compiled field middleware |
| 9 | Declared GraphQL type unlinked from resolver type | graphql-js `TResult = unknown` (§2.3); graphql-tools `IResolvers<any>` (§16) | generated signatures; builder `FieldDef<P, R>` ties `R` to `OutputRef<R>` |
| 10 | Generator rewriting user files | gqlgen stub merge (§17) | user `extends` generated abstract classes |
| 11 | Forgeable typestate | an extension type's representation is reachable by cast | `final class` + private constructor (§4.3) |
| 12 | AOT-only miscompile of sealed switches | dart-lang/sdk#56010 (doc 05 §6) | run the conformance suite under `dart compile exe` in CI |
| 13 | Throw-on-first-error parser | graphql-js #1426 (§2.1) | resilient parser + strict wrapper |
| 14 | Quadratic overlapping-fields validation | graphql-js #2185 (§2.4) | Sangria-derived algorithm |
| 15 | DataLoader dispatch timing on an eager runtime | ZQuery needs laziness (§11); JVM needs dispatch instrumentation (§7) | dispatch after the current microtask burst + executor-forced flush per level; test with resolvers that `await` before calling `load` |
| 16 | Introspection on by default in production | gqlgen opt-in (§17) | `introspection: IntrospectionPolicy` on the server, default off in release profiles |

### 19.6 Suggested build order
1. `graphql_language` (lexer, resilient parser, sealed AST, printer, visitors), proven against the graphql-js parser and printer tests plus fuzzing.
2. `graphql_schema` (SDL → model → `ValidSchema`, introspection types) and `graphql_validation` (ParallelVisitor rules plus the ported rule tests).
3. `graphql_execution` with the typed builder IR only (option B), already including `FutureOr`, the plan cache, middleware folding and subscriptions. Benchmark allocations here before any codegen exists.
4. `graphql_codegen` annotation front end (C), then the SDL front end (A), sharing one emitter.
5. `graphql_dataloader`, `graphql_server` (Extension chain, limits, APQ/trusted documents), `graphql_shelf` transports.
6. Incremental delivery (`executeIncrementally`, multipart/SSE), behind an opt-in flag, tracking graphql-spec#1110.
