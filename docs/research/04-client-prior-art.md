# 04. Client and codegen prior art

Date: 2026-10-13. Scope: typed GraphQL client design for a from-scratch, fully typed, spec-complete GraphQL implementation targeting Dart 3.x (sealed classes, records, pattern matching, extension types; no runtime reflection; build_runner/source_gen codegen; Dart macros were cancelled). Covers Apollo Kotlin (v4/v5), Apollo iOS, other Swift/Kotlin clients, graphql-code-generator, gql.tada, urql+graphcache, Apollo Client v4, Relay, Rust (cynic, graphql_client), and C# (Strawberry Shake), with a brief contrast against Dart's own ferry/graphql_codegen. Method: primary sources only — repositories cloned/inspected at specific commits via `git clone`/`gh api`, official documentation sites, CHANGELOGs, and live GitHub issues/PRs/releases, fetched by five parallel research passes and synthesized here. Every claim below is traceable to a cited source; version/commit identifiers are given where the fact is version-sensitive. ✅ = take directly, ⚠️ = adapt for Dart's constraints, ❌ = avoid / wrong fit.

## 0. In brief: the 15 most valuable patterns

1. **Default to operation-based, per-document-pruned codegen, never whole-schema response-based codegen.** Apollo Kotlin's `responseBased` mode caused exponential generated-code blowup through nested fragments and is no longer the default ([apollo-kotlin #3144](https://github.com/apollographql/apollo-kotlin/issues/3144)); graphql-code-generator's v6 client preset was redesigned specifically to prune unused schema types per document instead of emitting the whole schema ([migration guide](https://the-guild.dev/graphql/codegen/docs/migration/operations-and-client-preset-from-5-0)); Apollo iOS users report 400K LOC of generated Swift from heavy fragment use ([Anchorage eng blog](https://anchorage.com/insights/lessons-learned-using-graphql-for-ios)).
2. **Every union/interface/enum must carry a mandatory, exhaustive-switch-compatible "unknown" fallback variant.** Converges independently across every ecosystem studied: Apollo Kotlin's `OtherHero`/`UNKNOWN__`, Relay's `%future added value` enum sentinel and `__typename` discriminated unions, cynic's `#[cynic(fallback)]`, graphql_client's `#[serde(other)] Other(String)`. This is forward compatibility with an evolving server schema, not an edge case.
3. **Tri-state input wrapper is two variants over a nullable type, not three.** Apollo Kotlin's `Optional<T?>` (`Present<V>`/`Absent`) and Apollo iOS's `GraphQLNullable<T>` (`.none`/`.null`/`.some`) both express absent/null/value by wrapping a *nullable* payload type, not by having three enum cases — Apollo's own blog defends this explicitly ([GraphQLNullable is not a trap](https://www.apollographql.com/blog/graphqlnullable-is-not-a-trap)).
4. **Fragment masking converges on one mechanism everywhere it exists: an opaque wrapper type + an explicit unwrap function.** Relay's `$fragmentType`/`useFragment()`, graphql-codegen's `FragmentType`/`useFragment()`, gql.tada's `FragmentOf`/`readFragment()`, and Apollo Client v4's runtime `dataMasking`/`useFragment()` all do the same thing with different enforcement strength (type-level only in TS tooling vs. actual runtime field deletion in Relay/Apollo Client v4).
5. **A single shared backing map + typed façade gives masking, type-casting, and test mocks for free.** Apollo iOS's entire `SelectionSet`/`Fragments`/`asX` system is one trick: re-wrap the same `DataDict` as a narrower generated struct type, zero-copy, no re-decoding ([`SelectionSet.swift`](https://github.com/apollographql/apollo-ios/blob/main/Sources/ApolloAPI/SelectionSet.swift), [`FragmentProtocols.swift`](https://github.com/apollographql/apollo-ios/blob/main/Sources/ApolloAPI/FragmentProtocols.swift)); its test-mock system reuses the identical trick ([`TestMock.swift`](https://github.com/apollographql/apollo-ios/blob/main/Sources/ApolloTestSupport/TestMock.swift)).
6. **Declarative cache-key directive + an escape-hatch function, auto-injected into every selection at codegen time.** Apollo Kotlin's `@typePolicy`/`@fieldPolicy` ([declarative-ids.mdx](https://github.com/apollographql/apollo-kotlin/blob/main/docs/source/caching/declarative-ids.mdx)) and Apollo iOS's `@typePolicy` + `SchemaConfiguration.cacheKeyInfo(for:object:)` ([`SchemaConfiguration.swift`](https://github.com/apollographql/apollo-ios/blob/main/Sources/ApolloAPI/SchemaConfiguration.swift)) are the same two-tier design: schema directive for the common case, programmatic override for the rest.
7. **Scalar adapters are a trivial two-method interface, with compile-time *or* runtime registration, no reflection.** Apollo Kotlin's `Adapter<T>` (`fromJson`/`toJson`) can be wired as a generated static map or a runtime `Map`, both reflection-free ([custom-scalars.mdx](https://github.com/apollographql/apollo-kotlin/blob/main/docs/source/essentials/custom-scalars.mdx)); Strawberry Shake's two-sided `serializationType`/`runtimeType` + `ScalarSerializer<TValue>` is the same idea with an explicit wire/runtime type split.
8. **Chain-of-responsibility transport middleware, returning a stream (not a single future), with named insertion points.** Apollo Kotlin's `ApolloInterceptor.intercept(request, chain): Flow<ApolloResponse<D>>` with a four-value `InsertionPoint` enum ([`ApolloInterceptor.kt`](https://github.com/apollographql/apollo-kotlin/blob/main/libraries/apollo-runtime/src/commonMain/kotlin/com/apollographql/apollo/interceptor/ApolloInterceptor.kt)) got this right from day one because `@defer`/subscriptions need multi-emission; Apollo Client JS's `ApolloLink` (terminating vs. non-terminating) and urql's exchange pipeline are the single-response-era ancestors of the same idea.
9. **Normalized cache = flat Record store keyed by cache ID + cross-reference pointers, with explicit (not automatic) mark-and-sweep GC rooted at retained queries.** Relay's `RelayModernStore` (`retain`/`scheduleGC`/`_gcScheduler`) ([source](https://github.com/facebook/relay/blob/main/packages/relay-runtime/store/RelayModernStore.js)) and Apollo Kotlin's `ApolloStore.garbageCollect()` (`removeStaleFields`/`removeDanglingReferences`/`removeUnreachableRecords`) are architecturally identical designs arrived at independently.
10. **Optimistic updates are a separate overlay layer on the base store, not in-place mutation.** Relay's `RelayOptimisticRecordSource` sits above the base store and is rolled back on completion/failure, explicitly pausing GC while optimistic records are live ([source](https://github.com/facebook/relay/blob/main/packages/relay-runtime/store/RelayModernStore.js)).
11. **Error-aware codegen reifies "null because of error" vs. "really null" as a sealed Result type, not an ambiguous nullable field.** Apollo Kotlin's `@catch(to: RESULT|THROW|NULL)` → `FieldResult<T>` and Relay's `@catch`/`@required(action: THROW|LOG|NONE)` both implement this ahead of GraphQL-spec standardization ([nullability.mdx](https://github.com/apollographql/apollo-kotlin/blob/main/docs/source/advanced/nullability.mdx), [`required_directive.rs`](https://github.com/facebook/relay/blob/main/compiler/crates/relay-transforms/src/required_directive.rs)).
12. **Document-first codegen is the only architecturally honest choice without proc-macros/compile-time macros.** The cynic-vs-graphql_client contrast is the key lesson: cynic's derive-macro-validates-hand-written-struct-against-schema trick depends on Rust proc-macros expanding inline in the same compilation pass — a mechanism Dart does not have (macros cancelled) and `source_gen` cannot replicate exactly (it runs as a prior codegen pass over resolved elements, not an inline expansion).
13. **A whole-project, fragment-dependency-graph-aware compiler pass is required as soon as named fragments are reused/colocated across files** — not naive per-file codegen. This is *why* Relay rewrote its compiler from JS to Rust (5x–7x faster on a growing fragment graph, [intro blog](https://relay.dev/blog/2021/12/08/introducing-the-new-relay-compiler/)) and why Apollo Kotlin merges all `.graphql` files in a source set into one logical document before generating anything ([essentials/queries.mdx](https://github.com/apollographql/apollo-kotlin/blob/main/docs/source/essentials/queries.mdx)).
14. **Schema-shaped fake-data test builders, with a pluggable "fill unspecified fields" resolver, reusing the production backing-store trick.** Apollo Kotlin's `FakeResolver` (`resolveLeaf`/`resolveListSize`/`resolveMaybeNull`/`resolveTypename`), Apollo iOS's `Mock<O: MockObject>`, and Relay's `RelayMockPayloadGenerator` are three independent implementations of the same design.
15. **Codegen tooling and compiler extensibility should be a separate, swappable layer from the main build** — not a second native toolchain with its own install story. Relay's hard dependency on the external Watchman daemon repeatedly breaks across platforms ([#3674](https://github.com/facebook/relay/issues/3674), [#4874](https://github.com/facebook/relay/issues/4874)); Apollo Kotlin's compiler-plugin `ServiceLoader` mechanism and Apollo iOS's prebuilt-binary-vendored-separately-from-the-runtime-library split are both cleaner answers to "let third parties extend codegen without forking it."

## 2. Apollo Kotlin (v4/v5)

Cloned at commit [`afe947c`](https://github.com/apollographql/apollo-kotlin/commit/afe947c8aa77af4f02e24e8e53e7073ffa815be4) (2026-09-29). Per the in-repo [`CHANGELOG.md`](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/CHANGELOG.md), **v5 is no longer "in development" — it shipped**: v5.0.0 GA'd 2026-05-12, current is v5.2.0, and v4.4.x is maintenance-only ("most development is now made in the 5.x alpha," per the v4.4.0 changelog entry). v5 is framed as "incremental... most APIs are compatible with Apollo Kotlin 4," with breaking changes concentrated in Data Builders and Compiler Plugins.

**Declaration & Gradle wiring.** Exclusively file-based: `.graphql` operations, `.graphqls` SDL schemas (preferred over introspection JSON). All `.graphql` files in a source set are merged into **one logical document**, so operation/fragment names must be globally unique ([essentials/queries.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/essentials/queries.mdx)). The Gradle plugin (`apollo { service("name") { ... } }`) wires a `generateApolloSources` task per service; v5 moved compiler-worker isolation from GR8 jar-relocation to Gratatouille classloader isolation, targeting Gradle 9/AGP 9/KGP 2.3. ✅ take the file-based model; ⚠️ adapt the Gradle-specific plumbing into `build.yaml`.

**operationBased vs responseBased codegen.** Selected via `codegenModels` ([advanced/response-based.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/advanced/response-based.mdx)). `operationBased` (default) shapes classes after the *operation*, with inline-fragment branches as nullable sibling fields (`onDroid: OnDroid?`) — not an exhaustive sealed type. `responseBased` mirrors the *JSON response*: polymorphism becomes a Kotlin interface hierarchy (`Hero`/`DroidHero`/`HumanHero`/`OtherHero`), which is exhaustively `when`-able but is explicitly **not the default** because fragment nesting can cause exponential generated-code blowup past JVM class-size limits and breaks kapt on same-named nested interfaces ([#3144](https://github.com/apollographql/apollo-kotlin/issues/3144)). Separately, v5 added `generateApolloEnums` to render *enums* as a sealed interface with a `__Known` marker ([`EnumAsSealedInterfaceBuilder.kt`](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/libraries/apollo-compiler/src/main/kotlin/com/apollographql/apollo/compiler/codegen/kotlin/schema/EnumAsSealedInterfaceBuilder.kt), [#6611](https://github.com/apollographql/apollo-kotlin/issues/6611)). ⚠️ adapt — Dart's sealed classes + exhaustive `switch` make both Kotlin modes unnecessary as separate options: generate one sealed-class-per-union/interface with a mandatory `Unknown` fallback, always, without kapt/filename-length constraints forcing a second mode. ❌ avoid `operationBased`'s nullable-branch style specifically for unions/interfaces.

**No fragment masking.** Confirmed via maintainer response in [#6525 "Fragment-level data masking"](https://github.com/apollographql/apollo-kotlin/issues/6525): generated classes compose fragment fields as fully visible nested properties; there is no `useFragment()`-style unmasking step. A named fragment generates its own class plus a nullable accessor (`.launchFragment`) exposing all fields directly ([essentials/fragments.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/essentials/fragments.mdx)). ❌/note — useful as a negative data point: masking is an Apollo Client (JS)/Relay discipline, not inherent to "Apollo."

**`@typePolicy` cache keys.** `@typePolicy(keyFields: "id")` / `@fieldPolicy(forField:keyArgs:)`, imported via `@link(url: "https://specs.apollo.dev/cache/v0.4", ...)` ([caching/declarative-ids.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/caching/declarative-ids.mdx)); key fields are auto-injected into every selection at codegen time. ✅ take wholesale.

**Semantic nullability, `@catch`.** Experimental but functional ([advanced/nullability.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/advanced/nullability.mdx)): server-side `@semanticNonNull` → codegen emits a non-null Kotlin property; client-side `@catch(to: RESULT|THROW|NULL)` with `RESULT` wrapping the field as `FieldResult<T>` (`getOrNull()`/`getOrThrow()`/`graphQLErrorOrNull()`). v5.0.1 added `onError(OnError.NULL)` for finer partial-data control. ✅ take the three-way `@catch` behavior as a sealed Result concept; ⚠️ adapt away from Kotlin's exception-unwinding `THROW` option — Dart generated code should always reify, never throw mid-parse.

**`Optional<T>` tri-state.** `sealed class Optional<V>` with exactly `Present<V>(val value: V)` and `data object Absent` ([`Optional.kt`](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/libraries/apollo-api/src/commonMain/kotlin/com/apollographql/apollo/api/Optional.kt)); generated input constructor params for nullable fields are `Optional<T?>`, defaulted to `Optional.Absent`. ✅ take directly — a natural Dart sealed class, arguably cleaner via exhaustive `switch`.

**Scalar adapters.** Two-step: `mapScalar("GeoPoint", "com.example.GeoPoint")` in Gradle, then an `Adapter<T>` (`fromJson`/`toJson` over a streaming reader/writer) registered either compile-time (verbatim-injected expression) or runtime (`addCustomScalarAdapter`, keyed by generated `Types.X` token); built-in `AnyAdapter` is the dynamic-tree escape hatch ([essentials/custom-scalars.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/essentials/custom-scalars.mdx)). ✅ take wholesale — no reflection required either way.

**`UNKNOWN__` enums.** Default codegen appends a synthetic `UNKNOWN__` last constant when `withUnknown` is true ([`EnumAsEnumBuilder.kt`](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/libraries/apollo-compiler/src/main/kotlin/com/apollographql/apollo/compiler/codegen/kotlin/schema/EnumAsEnumBuilder.kt)); `safeValueOf(raw)` maps unknown values to it instead of throwing. ✅ take — but use a sealed class carrying the raw string (`Unknown(String rawValue)`), strictly better than a sentinel constant since Dart can't attach data to an `enum` case the way this needs.

**Errors model.** `ApolloResponse` carries `exception` (transport), `errors` (GraphQL array), `data` (possibly partial), with an authoritative 5-valid/3-impossible combination truth table ([essentials/errors.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/essentials/errors.mdx)); true-null vs. error-null is indistinguishable from `data` alone without cross-referencing `errors[].path` — precisely the gap `@catch` closes. ✅ take the three-field envelope + truth table as a direct contract.

**Normalized cache.** Moved out of the main repo into [`apollo-kotlin-normalized-cache`](https://github.com/apollographql/apollo-kotlin-normalized-cache) as of v5 ([migration-guide.md](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/caching/migration-guide.md)). `MemoryCache` (LRU, size/TTL limits) and SQLite-backed `SqlNormalizedCache` (SQLDelight, binary blobs in v5 — a **destructive, non-backward-compatible** schema change from pre-v5's JSON-text rows, requiring a manual migration script); cache layers are chainable (`memCache.chain(sqlCache)`), first-hit-wins reads, propagating writes. Records are rooted per operation type (`QUERY_ROOT`/`MUTATION_ROOT`/`SUBSCRIPTION_ROOT`) in v5 to avoid key collisions. GC is explicit: `ApolloStore.garbageCollect()` composes `removeStaleFields()`/`removeDanglingReferences()`/`removeUnreachableRecords()`, documented as a background-thread periodic task, not per-write ([caching/garbage-collection.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/caching/garbage-collection.mdx)). ✅ take the API shape (`CacheManager`/`Record`/`CacheKey`, chained layers, explicit non-automatic GC); ⚠️ adapt the SQLite layer to `sqlite3`/`drift`, and treat the destructive-migration history as a cautionary tale — version the on-disk format conservatively from day one.

**Interceptor chain.** `ApolloInterceptor.intercept(request, chain): Flow<ApolloResponse<D>>`, a recursive `DefaultInterceptorChain(interceptors, index)`, with each interceptor declaring an `InsertionPoint` (`BeforeCache`/`BeforeAutoPersistedQueries`/`BeforeRetryOnError`/`BeforeNetwork`) so third-party interceptors slot predictably ([`ApolloInterceptor.kt`](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/libraries/apollo-runtime/src/commonMain/kotlin/com/apollographql/apollo/interceptor/ApolloInterceptor.kt), v4.4.0 CHANGELOG #6767). ✅ take wholesale — a `Stream`-returning interceptor chain with ordered insertion points.

**WebSocket protocols & `@defer`.** Three protocols: legacy `SubscriptionWsProtocol` (still default for backward-compat despite being unmaintained upstream), modern `GraphQLWsProtocol` (`graphql-transport-ws`, can also run queries/mutations over the socket), and `AppSyncWsProtocol` ([essentials/subscriptions.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/essentials/subscriptions.mdx)); v5 promoted the modern stack to stable. `@defer`/`@stream` use Apollo's own pre-standardization incremental-delivery protocol (`incremental/v0.1` defer-only, `v0.2` defer+stream), selected via `incrementalDeliveryProtocol(...)` ([fetching/defer.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/fetching/defer.mdx)); `@defer` cannot be used with `responseBased` codegen (would require generating the model twice). ✅ take the `Stream<Response>`-of-incremental-payloads shape; ⚠️ adapt the wire protocol — it's proprietary and pre-standardization, use as an interop target, not the canonical spec.

**Persisted queries & data builders.** Both automatic persisted queries (SHA-256 hash-first, fallback to full POST) and build-time persisted-query manifests (`{id, body, name, type}` JSON for safelisting) are supported ([advanced/persisted-queries.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/advanced/persisted-queries.mdx)). Data builders (`generateDataBuilders`) generate a schema-shaped builder function per type (`buildHuman { ... }`) with unspecified fields auto-filled by a pluggable `FakeResolver` (`resolveLeaf`/`resolveListSize`/`resolveMaybeNull`/`resolveTypename`) ([testing/data-builders.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/testing/data-builders.mdx)). ✅ take both wholesale.

**Compiler plugins.** `ApolloCompilerPlugin` discovered via Java `ServiceLoader`, loaded in an isolated classpath, used by the external normalized-cache module to hook codegen without forking it ([advanced/compiler-plugins.mdx](https://github.com/apollographql/apollo-kotlin/blob/afe947c8aa77af4f02e24e8e53e7073ffa815be4/docs/source/advanced/compiler-plugins.mdx)). ⚠️ adapt the *intent* — a stable extension point for third-party codegen hooks — via `build.yaml`-registered `Builder`/`PostProcessBuilder`; ❌ avoid `ServiceLoader`/classloader-isolation mechanics, which are JVM-only.

**Build performance.** Real, ongoing pain documented in issues: exponential codegen blowup ([#3144](https://github.com/apollographql/apollo-kotlin/issues/3144)), large per-fragment adapter classes bloating APK size ([#5513](https://github.com/apollographql/apollo-kotlin/issues/5513)), an open ask to deduplicate fragment codegen ([#6588](https://github.com/apollographql/apollo-kotlin/issues/6588)), and codegen still **not** a true Gradle incremental task as of this writing ([#3658](https://github.com/apollographql/apollo-kotlin/issues/3658), open). Apollo's own v5.1.0 changelog entries are still cutting O(n²) schema-check costs and enum-lookup allocations. ⚠️ adapt — budget for file-granular incremental generation from day one, and expect codegen/parse performance to be ongoing engineering work, not a one-time fix.

## 3. Apollo iOS (Swift)

Cloned at commit [`431a15e`](https://github.com/apollographql/apollo-ios/tree/431a15e) (main, post-v2.4.0, Sept 2026).

**Declaration & tooling.** `.graphql` files discovered via glob search paths; the `apollo-ios-cli` ships as a **prebuilt binary tarball** ([`CLI/apollo-ios-cli.tar.gz`](https://github.com/apollographql/apollo-ios/tree/431a15e/CLI)) rather than source compiled in this repo — the actual codegen engine lives in a separate `apollo-ios-dev` monorepo. Config is JSON (`schemaDownload`, `input` glob, `output` targets). ✅ take — shipping a prebuilt generator binary avoids forcing every consumer through a heavy builder-time dependency graph, directly applicable to how a Dart CLI/builder should be packaged.

**Selection-set codegen shape.** Generated types are nested structs conforming to `SelectionSet` with a static `__selections: [Selection]` array and a `Fragments` associated type ([`SelectionSet.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/SelectionSet.swift)). Distinct protocols for `RootSelectionSet` (full field ownership), `InlineFragment` (type-case, inherited + type-specific fields), and `CompositeSelectionSet` (merged-fields-only). Every struct wraps a single untyped `DataDict` rather than storing typed properties directly — a metadata-driven execution model against one shared dict. ⚠️ adapt — the `Selection`-metadata + single-backing-map model maps well to Dart: an extension type over a `Map<String,Object?>` gives zero-cost typed views without reflection.

**Fragment masking & `asX` accessors.** The signature mechanic: a generated `Fragments` container exposes one property per named fragment (`var droidDetails: DroidDetails { _toFragment() }`), where `_toFragment()` is literally `T.init(_dataDict: __data)` — re-wrapping the *same* `DataDict` as a different struct type, no copy, no re-decoding ([`FragmentProtocols.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/FragmentProtocols.swift)). Type conditions use the identical trick: `asDroid: AsDroid?` on an interface/union field ([Type Conditions docs](https://www.apollographql.com/docs/ios/fetching/type-conditions)). ✅ take wholesale — a single decoded map behind extension-type façades, with safe-cast accessors generated per type condition/fragment, gives masking for free at zero runtime cost in Dart.

**Unions/interfaces as metadata objects.** `Union`/`Interface`/`Object` are value-type structs holding `name`/`possibleTypes`/`implementingObjects`, with `implements(_:)` checking membership by typename string, not protocol conformance ([`Union.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/SchemaTypes/Union.swift), [`Interface.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/SchemaTypes/Interface.swift)); polymorphism in generated *operation* models is handled entirely through `asX` optional accessors, not Swift enums over the result type. ⚠️ adapt — Dart 3 sealed classes + exhaustive `switch` are strictly better than string-typename checks; use real sealed unions for schema-type metadata while keeping the dict-masking trick for selection-set data.

**`@typePolicy` & cache keys.** `@typePolicy(keyFields: "id")` in schema SDL, composite keys space-separated/`+`-joined; `SchemaConfiguration.cacheKeyInfo(for:object:)` returns an optional `CacheKeyInfo(id:uniqueKeyGroup:)` as the programmatic escape hatch, defaulting to `nil` (normalization is opt-in per type); `uniqueKeyGroup` lets distinct types sharing an interface (e.g. `Dog`/`Cat` implementing `Pet`) share a cache-key namespace ([Cache Key Resolution docs](https://www.apollographql.com/docs/ios/caching/cache-key-resolution), [`CacheKeyInfo.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/CacheKeyInfo.swift)). ✅ take — the declarative-directive + escape-hatch-function two-tier design.

**`GraphQLNullable<T>` tri-state.** A three-case enum: `.none` (absent), `.null` (explicit JSON null), `.some(Wrapped)` (value) — conforming to all `ExpressibleBy...Literal` protocols, with `@dynamicMemberLookup` passthrough and a disfavored `??` overload ([`GraphQLNullable.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/GraphQLNullable.swift)); Apollo's own blog defends this explicitly against "just use `Optional<Optional<T>>`" criticism ([GraphQLNullable is not a trap](https://www.apollographql.com/blog/graphqlnullable-is-not-a-trap)). ✅ take — portable to Dart as a 3-case sealed class (`Absent`/`Null`/`Present(T)`); Dart lacks `@dynamicMemberLookup` but extension methods approximate the ergonomics.

**Custom scalars & enums.** Scalar mapping associates a schema scalar name with a user Swift type conforming to a `CustomScalarType`-style protocol at generation time. ⚠️ adapt — same pattern fits Dart via a user-supplied codec keyed by scalar name in `build.yaml`. Enums are wrapped as `GraphQLEnum<T>` where `T: EnumType` is the raw generated enum — an unrecognized server value is preserved rather than crashing decode. ✅ take — a sealed class with a catch-all `UnknownEnumValue(String raw)` variant is a direct, arguably superior, Dart translation (free exhaustiveness checking).

**Errors model.** `GraphQLError` wraps a raw `JSONObject`, exposing `message`/`locations`/`path`/free-form `extensions` via subscript rather than force-decoding into a rigid struct — so custom server `extensions` never break the client ([`GraphQLError.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/Apollo/GraphQLError.swift)). Field paths use `ResponsePath`, implemented as an **immutable reverse linked list** rather than an array, per an in-source comment citing a decoding performance bottleneck with arrays ([`ResponsePath.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloAPI/ResponsePath.swift)). ✅ take the raw-JSON-passthrough-for-extensions idea; ⚠️ adapt the linked-list path representation — benchmark in Dart before copying, since `List` performance characteristics differ from Swift arrays.

**Normalized cache.** `NormalizedCache` protocol is fully `async`: `loadRecords`/`merge` (returns changed *field* keys like `QUERY_ROOT.Foo.myField` for fine-grained watcher invalidation)/`removeRecord(s)`/`clear` ([`NormalizedCache.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/Apollo/Caching/NormalizedCache.swift)). Two implementations: `InMemoryNormalizedCache` and `ApolloSQLiteDatabase` (pluggable `SQLiteDatabase` protocol for encryption/compression wrapping). ✅ take the key-returning merge + typed read-only vs. read-write transaction split as a clean cache contract.

**Transport.** HTTP via `URLSession`; subscriptions specifically use **`graphql-transport-ws`** ([CHANGELOG v2.1.0](https://github.com/apollographql/apollo-ios/blob/431a15e/CHANGELOG.md)). `@defer` is supported via `MultipartResponseDeferParser.swift`/`IncrementalGraphQLResult.swift`, with a v2.3.0 fix for deferred-path-to-cache-key resolution confirming it's a maintained, cache-integrated feature. File uploads implement the [GraphQL multipart request spec](https://github.com/jaydenseric/graphql-multipart-request-spec) via `GraphQLFile`/`MultipartFormData`/`UploadRequest.swift`. ✅ take all three — an `HttpClient` abstraction over any HTTP stack, `graphql-transport-ws` over `package:web_socket_channel`, and the jaydenseric multipart spec, which is the de facto cross-ecosystem standard.

**Test mocks.** `ApolloTestSupport` generates a `Mock<O: MockObject>` per schema object, `@dynamicMemberLookup`-keyed, backed by an untyped `_data: [String: AnyHashable]` dict ([`TestMock.swift`](https://github.com/apollographql/apollo-ios/blob/431a15e/Sources/ApolloTestSupport/TestMock.swift)) — the same backing-dict trick reused for fixtures. ✅ take — generating a fixture-builder type with the identical backing-store trick as the real model.

**Build performance complaints.** [#2740](https://github.com/apollographql/apollo-ios/issues/2740) ("Generated code size... exponentially large"), [#3388](https://github.com/apollographql/apollo-ios/issues/3388) (slow compilation after migration), [#3434](https://github.com/apollographql/apollo-ios/issues/3434) (codegen fails with many nested fragments), migration megathread [#2678](https://github.com/apollographql/apollo-ios/issues/2678); third-party corroboration from Anchorage's engineering blog reporting **400K LOC** of generated Swift taking minutes to compile ([Lessons Learned Using GraphQL for iOS](https://anchorage.com/insights/lessons-learned-using-graphql-for-ios)). Apollo's 1.0 rewrite and 1.7.0's parallelized async/await codegen engine were direct responses. ❌ avoid the failure mode — keep per-file generated output small, design for incremental/on-demand generation per operation file.

### Other notable Swift/Kotlin typed clients

- **AWS Amplify GraphQL codegen**: schema-first (not operation-first), AppSync-coupled model-generation CLI across Swift/Android/Flutter ([docs](https://docs.amplify.aws/cli/graphql/client-code-generation/)). ⚠️ adapt the CLI-driven, per-platform-target codegen UX; too AppSync-specific to port wholesale.
- **swift-graphql-codegen** ([pm-dev/swift-graphql-codegen](https://github.com/pm-dev/swift-graphql-codegen)): small/niche, zero-runtime-dependency, direct `Codable` decoding (no backing-dict indirection), SwiftPM build-tool-plugin integration. ✅ take the "zero-copy, build-plugin-integrated" design value; too small-scale to be proven prior art.
- **kgql** ([yshrsmz/kgql](https://klibs.io/project/yshrsmz/kgql)): KMP Gradle plugin wrapping `.gql` into Ktor request classes, ~4 years stale. ❌ avoid — effectively unmaintained.
- **Kobby**: Kotlin DSL-based codegen generating a fluent query-builder instead of string documents. ⚠️ adapt only the DSL-builder idea if programmatic query construction is ever wanted in Dart.
- No other noteworthy dedicated typed Swift GraphQL client was found; the non-Apollo Swift ecosystem is thin.

## 4. graphql-code-generator (TypeScript)

**`TypedDocumentNode`.** Defined in the standalone package [`graphql-typed-document-node`](https://github.com/dotansimha/graphql-typed-document-node): a plain `DocumentNode` with two **phantom type parameters**, `TData`/`TVariables` — the runtime object is identical to an untyped `DocumentNode`; any client function typed to accept `TypedDocumentNode<TData,TVariables>` gets free generic inference with zero runtime cost. Consumed by `@apollo/client`, `@urql/core`, `apollo-angular`, `graphql-request`. ✅ take — this is a generic-parameter trick directly portable as a Dart generated wrapper/extension type carrying `TData`/`TVars` type parameters around the parsed document.

**Client preset & masking.** `@graphql-codegen/client-preset` is the current recommended setup (v6, [migration guide](https://the-guild.dev/graphql/codegen/docs/migration/operations-and-client-preset-from-5-0)). Operations/fragments are written inline via a generated `graphql()` tagged function, fragments co-located and referenced by name without re-declaring fields. When the source is a fragment, the inferred result carries an opaque `FragmentType<typeof F>` marker instead of real fields ([the-guild blog](https://the-guild.dev/blog/unleash-the-power-of-fragments-with-graphql-codegen)); `useFragment(FragmentDoc, maskedData)` is the sanctioned unwrap. ⚠️ adapt — maps well to Dart `extension type`s, which are genuinely opaque at the type level (stronger than TS's structural typing).

**The v6 redesign's real difference.** Legacy `typescript-operations` generated all schema types upfront regardless of use, causing large files; `near-operation-file` emits one file per source file but still couples to the central schema-types file; the v6 client preset generates schema types **only when actually used**, decoupling from `typescript`/`typescript-resolvers` and integrating `TypedDocumentNode` + masking into one preset with "one-file/multi-file/near-operation-file" output modes from a single config ([migration guide](https://the-guild.dev/graphql/codegen/docs/migration/operations-and-client-preset-from-5-0)). ✅ take the per-operation, usage-pruned, co-located output design directly for how a build_runner builder should scope generation.

**Scalars, enums, errors.** Custom scalars default to `any` unless mapped via a `scalars` config block; enums can be native TS `enum`, `const enum`, or string-union, with the docs themselves recommending `enumsAsTypes: true` because native enums don't tree-shake and numeric enums lose the wire-value mapping ([typescript plugin docs](https://the-guild.dev/graphql/codegen/plugins/typescript)). ❌ avoid porting native-enum-equivalent codegen to Dart — sealed classes with exhaustive `switch` sidestep the whole footgun class. GraphQL `errors[]` is **not typed at all** by codegen — an acknowledged ecosystem gap, with The Guild's own blog recommending schema-level error unions instead ([GraphQL error handling with fp-ts](https://www.the-guild.dev/blog/graphql-error-handling-with-fp)). ⚠️ adapt — a Dart client should model `errors` explicitly via a `GraphQLResponse<T>` envelope rather than copy this gap.

**Performance/size complaints.** [#10466](https://github.com/dotansimha/graphql-code-generator/issues/10466) (open): watch mode re-runs *all* generate tasks on any change, no per-file scoping. [#9988](https://github.com/dotansimha/graphql-code-generator/issues/9988) (open): client-preset's `graphql.ts` embeds operation-string lookup tables twice, defeating tree-shaking/code-splitting. Yelp's engineering blog documents a monorepo issue where Codegen duplicates output across packages consuming the same co-located fragment ([Yelp eng blog](https://engineeringblog.yelp.com/2026/07/migrating-to-graphql-codegen.html)). ❌ avoid replicating — scope regeneration to build_runner's native file-level incrementality, and never duplicate literal query-string bytes per build target.

## 5. gql.tada

**The core trick.** Per the project itself, gql.tada "parses your GraphQL documents in the TypeScript type system, uses your introspected schema and scalar configuration to derive a schema, maps your GraphQL queries and fragments... to result and variables types, [and] creates fragment masks" entirely via TS's type-level template-literal parsing and conditional types, evaluated live by the type checker ([README](https://raw.githubusercontent.com/0no-co/gql.tada/main/README.md)). `graphql()` must come from gql.tada's own import — the trick depends on the exact literal string type being visible to a specific generic signature.

**There is still a build step — a lighter one.** The schema is materialized into an output typings file (default `graphql-env.d.ts`), "preprocessed into an intermediary format" recommended over raw JSON for type-checker efficiency on large schemas ([workflows doc](https://raw.githubusercontent.com/0no-co/gql.tada/main/website/get-started/workflows.md)). Produced by the `gql.tada/ts-plugin` TS Language Service plugin while editing, or on-demand via `gql-tada generate output`/`generate schema <url>`/`check`/`doctor` CLI commands for CI — because **`tsc` itself does not load TS Language Service plugins**, only editors do. The honest framing: codegen's build step produces executable code; gql.tada's build step produces one schema-shaped type-cache file every document type-checks against.

**Masking mechanics & limitations.** `FragmentOf<typeof frag>` / `readFragment()` is structurally identical in spirit to graphql-codegen's `FragmentType`/`useFragment` — same opaque-wrapper trick, derived instead of generated ([API reference](https://raw.githubusercontent.com/0no-co/gql.tada/main/website/reference/gql-tada-api.md)). Documented limitations: TS <5.5 needs a separate plugin install; the Language Service plugin **cannot run inside `.vue`/`.svelte` files** without extra support packages; workspace (not global) TS version required in VS Code ([installation guide](https://gql-tada.0no.co/get-started/installation)).

**Philosophical comparison.** gql.tada inverts codegen's dependency direction: "schema → one type-cache artifact → every operation's types computed on-demand by the compiler," eliminating per-operation generated files at the cost of pushing real work onto `tsc`/the language server per file. ❌ avoid literal port — Dart has no type-level string-literal parser or conditional-type engine (macros cancelled; `extension type` is zero-cost but not computational over string literals), so this mechanism is structurally inapplicable. ✅ take the *idea* of a single committed schema-derived artifact every operation builder depends on, and the opaque-`FragmentType`/unwrap-function masking pattern — both portable via `source_gen`.

## 6. urql + graphcache

**Exchange architecture.** `Client` dispatches an `Operation` through an ordered `Exchange[]` pipeline built on `wonka` observables — urql's analogue of Apollo's link chain ([`@urql/core` API](https://raw.githubusercontent.com/urql-graphql/urql/main/docs/api/core.md)); `cacheExchange` sits before the terminating `fetchExchange`, and `client.reexecuteOperation` is how a cache tells the client to rerun an operation after invalidation.

**Graphcache.** A drop-in replacement `cacheExchange` for normalized caching ([README](https://raw.githubusercontent.com/urql-graphql/urql/main/docs/graphcache/README.md)): `keys` (per-typename custom cache-key extraction, overriding default `id`/`_id` heuristics), `resolvers` (local resolvers for computed values/pagination/redirects), `updates` (a `{ Mutation: { field(result,args,cache,info) } }` map of updater functions calling `cache.link`/`writeFragment`/`invalidate`), and `optimistic` (provisional-data functions applied before the real response lands). As of v7, mutations with no configured updater fall back to invalidating same-`__typename` entities when a new entity appears ([Cache Updates doc](https://raw.githubusercontent.com/urql-graphql/urql/main/docs/graphcache/cache-updates.md)).

**Schema-aware invalidation.** Passing an introspected schema unlocks deterministic fragment matching on unions/interfaces, config-typo validation, and **partial results**: Graphcache can satisfy a query partially from cache (marked `stale`) while fetching the rest, because the schema states which fields are nullable ([Schema Awareness doc](https://raw.githubusercontent.com/urql-graphql/urql/main/docs/graphcache/schema-awareness.md)).

**vs. Apollo InMemoryCache.** Graphcache auto-traverses the document + `__typename`+key with zero required config; Apollo's cache requires explicit, up-front `TypePolicies`. ✅ take the layered-opt-in design (works with zero config, add `keys`/`resolvers`/`updates`/`schema` only as needed), and schema-aware partial-result/stale-flag semantics as a target feature. ⚠️ adapt the `updates`/`optimistic` function-map shape as sealed-class-dispatched callbacks in Dart, gaining exhaustiveness TS can't offer.

## 7. Apollo Client v4 (JavaScript/TypeScript)

**Release status**, verified via the GitHub Releases API: `@apollo/client@4.0.0` GA'd 2025-08-21; the series reached `4.3.3` on 2026-10-08 ([releases](https://github.com/apollographql/apollo-client/releases)) — actively maintained, not beta.

**Data masking.** Enabled via `new ApolloClient({ dataMasking: true, ... })`; masked fields are hidden from components, accessible only via `useFragment()` ([Fragments docs](https://www.apollographql.com/docs/react/data/fragments)). A `TypeOverrides` augmentation aligns with graphql-codegen's output, but Apollo's docs state its own masking is **incompatible** with graphql-codegen's client-preset masking — pick one, not both. Critically, unlike graphql-codegen/gql.tada's type-level-only erasure, Apollo Client v4's masking (following Relay's lead) **actually deletes/hides fields from the runtime object**, enforced at both type and runtime levels. ✅ take runtime-enforced masking as the stronger model — trivial to do losslessly in Dart given real sealed/closed object construction. ⚠️ adapt the dual-masking-systems-conflict lesson: design exactly one masking mechanism for Dart.

**Link chain.** The canonical middleware-chain pattern: a terminating link (`HttpLink`/`BatchHttpLink`) vs. non-terminating links (`RetryLink`, `ErrorLink`) that call `forward(operation)`, composed via `ApolloLink.from([...])` ([Apollo Link overview](https://www.apollographql.com/docs/link/)). ✅ take — a `GraphQLLink` abstract class with a `forward` callback is a clean, well-understood shape to mirror in Dart.

**`@defer`/incremental delivery.** GA (preview since 3.7), multipart HTTP, client configures a format handler (`Defer20220824Handler`/`GraphQL17Alpha2Handler`) matching the server's wire format — two incompatible incremental-delivery spec versions already coexist ([`@defer` docs](https://www.apollographql.com/docs/react/data/defer)). ⚠️ adapt — isolate format-handler versioning behind a pluggable interface, don't hardcode one wire format.

**Cache field policies.** `InMemoryCache` takes `TypePolicies` keyed by type name, each field with `read`/`merge` functions and `keyArgs` (which arguments participate in that field's cache key) ([Customizing cached fields](https://www.apollographql.com/docs/react/caching/cache-field-behavior)). ✅ take `read`/`merge`/`keyArgs` as the extensibility seam for a Dart normalized cache, noting masking must leave cache APIs untouched (masked fields still readable/writable by cache policies).

## 8. Relay compiler

**Tagged templates + whole-project compiler.** The `graphql` tagged template is colocated in component files; a Babel plugin only swaps the tag for a generated-module reference — it does **not** do codegen. The actual codegen is a separate whole-project Rust compiler (`relay-compiler`; crates: `graphql-ir`, `relay-transforms`, `relay-typegen`, `relay-codegen`, `dependency-analyzer` — [crates tree](https://github.com/facebook/relay/tree/main/compiler/crates)), with a dedicated `extract-graphql` crate walking raw source char-by-char to pull out `graphql\`...\`` literals before any JS parser runs ([source](https://github.com/facebook/relay/blob/main/compiler/crates/extract-graphql/src/lib.rs)). A whole-project pass is required because a query is assembled by stitching together every component's fragment across the render tree ([compiler guide](https://relay.dev/docs/guides/compiler/)). Meta rewrote this from JS to Rust in 2020 because Node has no true shared-memory multithreading and a single-threaded compiler couldn't scale with a growing fragment graph — "nearly 5x better on average, nearly 7x at P95" ([intro blog](https://relay.dev/blog/2021/12/08/introducing-the-new-relay-compiler/)). ✅ take the project-wide, dependency-graph-aware compiler architecture for Dart, since build_runner's per-library default doesn't naturally support cross-file fragment composition — argues for a custom aggregate builder phase resolving a global fragment graph before per-file emission.

**Fragment colocation as mandate.** Without it, components have implicit, unenforced data dependencies ([thinking-in-relay](https://relay.dev/docs/principles-and-architecture/thinking-in-relay/)); because every component's fragment is statically known, the compiler determines the whole view's data requirements before runtime and issues a single network request instead of serial fetching. ⚠️ adapt — Dart/Flutter has no JSX-equivalent convention to colocate fragments *in*; worth adopting the idea (static, mandatory per-widget data declarations) as a deliberate convention/lint, not something the language enforces by default.

**Fragment masking.** Verified in a generated artifact: Relay emits an opaque type per fragment (`declare export opaque type X$fragmentType: FragmentType;`), and the parent's `$data` type carries only `$fragmentSpreads: X$fragmentType` instead of real fields ([generated example](https://github.com/facebook/relay/blob/main/packages/relay-test-utils/__tests__/__generated__/RelayMockPayloadGeneratorTestNameRendererFragment.graphql.js)) — masking enforced at the type level, not cooperatively. `useFragment(fragmentDef, fragmentRef)` unwraps via the store. ✅ take — opaque-type fragment refs map directly onto Dart extension types: a zero-cost wrapper exposing no public fields except via generated typed accessors, arguably a better fit than in TS/Flow.

**Normalized store, GC, optimistic updates.** Default `dataID` is `fieldValue.id` (a `VIEWER_ID` sentinel for the singleton `Viewer` type) — overridable, not hard-required to follow the `Node` interface ([`defaultGetDataID.js`](https://github.com/facebook/relay/blob/main/packages/relay-runtime/store/defaultGetDataID.js)). `RelayModernStore` keeps flat records keyed by `dataID`, running mark-and-sweep GC: `retain(operation)` pins roots, a `_gcScheduler` sweeps unreachable records, explicitly skipping GC while optimistic updates are applied ([source](https://github.com/facebook/relay/blob/main/packages/relay-runtime/store/RelayModernStore.js)). Optimistic updates write through a separate `RelayOptimisticRecordSource` layered over the base store; sequence is optimistic write → optimistic updater → (success) rollback → real write → real updater → `onCompleted` ([mutations guide](https://relay.dev/docs/guided-tour/updating-data/graphql-mutations/)). ✅ take normalization-by-ID + flat record store + mark-sweep GC rooted at retained queries, and optimistic-layer-over-base-store for safe rollback; ⚠️ adapt the ID convention to be pluggable rather than hard-requiring a `Node` interface.

**`@refetchable`/connections.** `@refetchable` is its own transform (`refetchable_fragment.rs`) turning a fragment into a standalone refetch root query; connections require `edges { cursor node }` + `pageInfo` per the Cursor Connections spec, with `usePaginationFragment` wrapping `useFragment` + a generated refetch query to expose `hasNext`/`loadNext`/`isLoadingNext` while the store auto-appends pages ([pagination guide](https://relay.dev/docs/guided-tour/list-data/pagination/)). ✅ take the connection-spec contract + compiler-synthesized refetch query + store-side auto-append, as a Dart builder output + `PaginationController` runtime class.

**Unions/interfaces, enums.** Generated types discriminate on `__typename` plus a synthetic `__isActor: "Page"`-style marker for interface-implementing types ([generated example](https://github.com/facebook/relay/blob/main/packages/relay-runtime/mutations/__tests__/__generated__/validateMutationTestIsActorMutation.graphql.js)). Enums generate a string-literal union **plus** a `"%future added value"` forward-compatibility sentinel ([generated example](https://github.com/facebook/relay/blob/main/packages/relay-test-utils/__tests__/__generated__/RelayMockPayloadGeneratorTest39Query.graphql.js)). ✅ take both patterns directly onto Dart sealed classes with exhaustive `switch` — compiler-enforced exhaustiveness Relay's generated TS/Flow types can only approximate via lint discipline.

**Errors: `@required`/`@catch`.** `@required(action: THROW|LOG|NONE)` bubbles null up the tree; `@catch(to: NULL|RESULT)` catches a field's error as `null` or a Result-like value — ahead of base-spec standardization (`relay-transforms/src/required_directive.rs`, `catch_directive.rs`). ✅ take wholesale — translates almost verbatim to Dart sealed `Result` types.

**`@defer`/`@stream`.** Implemented as IR transforms carrying `label`/`if`/`initial_count`, each branch getting a unique label correlating incremental payloads back to the response tree (`defer_stream.rs`); runtime couples this with React Suspense (`usePreloadedQuery`, nested `<Suspense>`). Subscriptions compose with `@defer`/`@stream` through the same normalized-store pipeline. ✅ take the label/path incremental-patch model as a normalized-store write strategy; ❌ avoid the React Suspense coupling specifically — Flutter has no Suspense equivalent, expose incremental resolution as a plain `Stream` the widget layer subscribes to.

**Persisted queries, test utilities.** A dedicated `persist-query` crate posts operation text to a persistence endpoint expecting `{"id": "<hash>"}` back ([source](https://github.com/facebook/relay/blob/main/compiler/crates/persist-query/src/lib.rs)); local mode hashes into a `queryMap.json`, sending `{doc_id, variables}` over the wire instead of full text ([persisted-queries guide](https://relay.dev/docs/guides/persisted-queries/)). `relay-test-utils` provides `RelayMockPayloadGenerator` (auto fixture generation matching a query's shape) and `RelayModernMockEnvironment` (fully controllable in-memory network layer). ✅ take both wholesale.

**Build/DX complaints.** Generated-artifact bloat ("same size as source, maybe bigger," [#2276](https://github.com/facebook/relay/issues/2276), open split-artifact request [#5190](https://github.com/facebook/relay/issues/5190)); no partial multi-project compilation forcing full CI rebuilds ([#3796](https://github.com/facebook/relay/issues/3796)); repeated breakage from the hard Watchman dependency across platforms ([#3674](https://github.com/facebook/relay/issues/3674), [#4874](https://github.com/facebook/relay/issues/4874), [#4907](https://github.com/facebook/relay/issues/4907), [#4545](https://github.com/facebook/relay/issues/4545)). ⚠️ adapt — avoid a second, independent native toolchain with its own install/version story; keep file-watching inside build_runner's existing watch mode. ✅ take the lesson to budget for generated-artifact size and make project-scoped/partial builds first-class from day one.

## 9. cynic (Rust)

[obmarg/cynic](https://codeberg.org/obmarg/cynic) ([docs](https://cynic-rs.dev)) inverts the usual flow: **Rust structs are the query**, derived against a schema. A schema is loaded at build time (`cynic::use_schema!(...)` or `cynic_codegen::register_schema` from `build.rs`), expanding phantom marker types per GraphQL type/field. `#[derive(cynic::QueryFragment)]` walks a struct's fields and cross-references each against the schema module ([`fragment_derive/mod.rs`](https://codeberg.org/obmarg/cynic/src/branch/main/cynic-codegen/src/fragment_derive/mod.rs)); fields not on the target type become `compile_error!` diagnostics with "did you mean" suggestions ([`suggestions`](https://codeberg.org/obmarg/cynic/src/branch/main/cynic-codegen/src/suggestions)) — real, line-accurate compile-time schema validation of a hand-written struct shape. Unions/interfaces are modeled as an `enum` via `#[derive(cynic::InlineFragments)]`, one variant per possible type plus a mandatory `#[cynic(fallback)]` variant. Inputs use `#[derive(cynic::InputObject)]` (including `oneOf` modeled as an enum); custom scalars via `#[derive(cynic::Scalar)]` or `cynic::impl_scalar!`; enums via `#[derive(cynic::Enum)]` with `#[cynic(fallback)]` (unit, or tuple `Unknown(String)`); subscriptions delegate transport to the companion [`graphql-ws-client`](https://codeberg.org/obmarg/graphql-ws-client) crate.

**Verdict: ⚠️ adapt, with a correction to the naive assumption.** A literal proc-macro-for-derive doesn't exist in Dart and Dart macros were cancelled, so cynic's exact mechanism (expansion at the token level, inline in the same compilation pass as the annotated type) cannot be ported 1:1. But `source_gen` is not powerless: a `Builder` running on the analyzer's resolved element model sees a class's real field names/types/nullability — the same richness `syn`+schema markers give cynic — so a builder *can* validate an annotated Dart class's fields against a schema and emit `InvalidGenerationSourceError` pointing at the exact source span, with did-you-mean suggestions, as a build_runner step. The real differences: it's a prior codegen pass, not a live-as-you-type diagnostic, and it still needs a generated `.g.dart` output since Dart cannot synthesize methods onto the original class without macros. Take the *idea* (struct-shape-is-the-query validated against schema, enum+fallback forward-compat, `oneOf`-as-enum inputs); don't expect cynic's single-compile-pass ergonomics.

## 10. graphql_client (Rust)

[graphql-rust/graphql-client](https://github.com/graphql-rust/graphql-client) is the conventional document-first approach: `.graphql` query files + `#[derive(GraphQLQuery)]` pointed at both query and schema ([README](https://github.com/graphql-rust/graphql-client/blob/main/README.md)):
```rust
#[derive(GraphQLQuery)]
#[graphql(schema_path = "...", query_path = "...")]
pub struct UnionQuery;
```
generates a module with a `ResponseData` root, `Variables`, and one nested struct/enum per selection set — response types nest **per-operation**, comparable to Apollo Kotlin/Apollo iOS's per-operation nesting. Custom scalars default to Rust built-ins; otherwise require a matching type in scope or a `custom_scalars_module` ([`codegen_options.rs`](https://github.com/graphql-rust/graphql-client/blob/main/graphql_client_codegen/src/codegen_options.rs)). Enums generate a `#[serde(other)] Other(String)` catch-all ([`enums.rs`](https://github.com/graphql-rust/graphql-client/blob/main/graphql_client_codegen/src/codegen/enums.rs)). Errors use a fixed `Response<Data> { data, errors, extensions }` envelope matching the spec exactly ([`lib.rs`](https://github.com/graphql-rust/graphql-client/blob/main/graphql_client/src/lib.rs)). Normalized cache is confirmed absent — purely codegen+transport-adjacent, state management left to the caller. `deprecated = "allow"|"warn"|"deny"` turns deprecated-field usage into a hard compile error.

**Verdict: ✅ take as the baseline architecture.** Document-first + schema-checked codegen into per-operation nested types is exactly the shape that's mechanically realistic for `build_runner`/`source_gen`: a builder reads `.graphql` + schema, no analyzer-introspection-of-hand-written-classes trick required.

### cynic vs graphql_client

The split is derive-first (schema → you write the shape, it's checked) vs. document-first (you write the query, the shape is generated). cynic optimizes for structural reuse at the cost of its own marker-type/attribute DSL; graphql_client optimizes for the familiar GraphQL-tooling workflow at the cost of no cross-operation structural sharing beyond `.graphql`-level fragments. For a Dart client where `build_runner`/`source_gen` is the only generation story — no macros to splice derive-time validation onto arbitrary hand-written classes the way cynic does — **document-first is the architecturally honest choice**; a cynic-*flavored* ergonomic layer (schema-checked field names, sealed-class unions with exhaustive fallback) can still be borrowed as surface API design even though the generation pipeline underneath is necessarily document-first.

## 11. Strawberry Shake (C#)

[ChilliCream/graphql-platform](https://github.com/ChilliCream/graphql-platform), `src/StrawberryShake`. **Current status, verified from primary sources**: actively developed as of research date — commits touching StrawberryShake as recently as 2026-09-25 ([#10414](https://github.com/ChilliCream/graphql-platform/pull/10414)), pre-release packages shipping multiple times a week (`16.7.0-p.26` published 2026-10-13, the same day as this research, via the GitHub releases API). Older community threads about "uncertain investment" do not match the current commit/release cadence.

**Architecture.** `.graphql` files compiled by the `StrawberryShake.Tools` dotnet CLI (`dotnet graphql init <url>`), configured via `.graphqlrc.json`, codegen running as an MSBuild step. Results normalize into a client-side **entity store**: Generated Client → Operation Store → Entity Store → GraphQL Server, with three execution strategies (`NetworkOnly`/`CacheFirst`/`CacheAndNetwork`), settable globally or per-call. The generated client exposes `IObservable`-style `.Watch().Subscribe(...)`, plus Blazor components with `ChildContent`/`ErrorContent`/`LoadingContent` slots. Custom scalars use a two-sided model: `serializationType` (wire) vs. `runtimeType` (.NET), declared via `@serializationType`/`@runtimeType` schema-extension directives with a `ScalarSerializer<TValue>` base class. Subscriptions reuse the same `.Watch().Subscribe()` API over a separate `StrawberryShake.Transport.WebSockets` package.

**Verdict: ⚠️ adapt.** The entity-store/normalized-cache + reactive-watch model is proven and directly analogous to what ferry already does in Dart — worth studying for the three-strategy API surface and the two-sided scalar serializer design, both cleaner than most Dart equivalents. Not a ✅ because the reactive layer is built on `IObservable`/Rx idioms and MSBuild-integrated multi-file codegen that don't map directly onto Dart's `Stream`-based idioms or build_runner's single-pass-per-file model — a design-pattern reference, not portable code/tooling.

## 12. Dart ecosystem — brief contrast (ferry, graphql_codegen)

**ferry** ([gql-dart/ferry](https://github.com/gql-dart/ferry)) generates one immutable `built_value` data class per operation (`G<OperationName>Data`, e.g. [`reviews.data.gql.dart`](https://github.com/gql-dart/ferry/blob/master/packages/ferry_test_graphql2/lib/queries/__generated__/reviews.data.gql.dart)), paired with a normalized cache in `ferry_cache` (id-based normalization over `packages/normalize`). This is Apollo/Relay-style: per-operation generated types backed by a shared normalized store, reactive via `Stream`-based watch queries — the closest existing Dart analogue to Strawberry Shake's entity store, built on `built_value` rather than records/sealed classes.

**graphql_codegen** ([heftapp/graphql_codegen](https://github.com/heftapp/graphql_codegen), pub.dev v3.0.2) is "simple, opinionated" codegen: `fromJson`/`toJson` data classes, fragment classes, and client-helper functions directly per `.graphql` document, plus `readFragment`/`writeFragment` cache-access helpers integrating with the existing `graphql`/`graphql_flutter` package's cache rather than shipping its own normalized store — pure request/response codegen (closer to graphql_client's philosophy), bring-your-own cache.

Both already validate that per-operation nested generated types work fine with `build_runner`/`source_gen` in production Dart today; the open design decision for a new client is ferry's pattern (operation-scoped class + integrated normalized cache) vs. graphql_codegen's pattern (operation-scoped class + bring-your-own cache).

## 13. Synthesis: recommended client design for Dart

**How operations should be declared.** Document-first, `.graphql` files, is the only architecturally honest choice (§10, cynic vs. graphql_client). Dart has no proc-macro/compile-time-macro mechanism (cancelled) to splice cynic-style derive-time schema validation onto hand-written structs inline; `source_gen` can still perform schema-checked validation with did-you-mean diagnostics, but only as a prior codegen pass over the analyzer's resolved element model, not an inline expansion. Reject a runtime query-builder DSL as the primary interface (no ecosystem studied uses one as primary, and it forfeits static analysis of the operation against the schema at edit time). On the specific question of build_runner vs. a standalone CLI (the "typed_openapi ships ready-made code without mandatory build_runner" option): factor the actual codegen logic into a pure Dart library with two thin entry points — a `build_runner`/`source_gen` `Builder` (the idiomatic default for Dart packages, matching `json_serializable`/`freezed`/`built_value` convention, and giving incremental watch-mode for free) and a standalone CLI wrapping the same library for CI, non-build_runner consumers, and schema/query linting. This mirrors two things found in the research: Relay's own split between a thin Babel plugin and a separate whole-project Rust compiler binary (§8), and Apollo iOS's decision to vendor a prebuilt CLI binary separately from the runtime library (§3). Ship both from day one — the CLI is nearly free once the engine is factored out this way, not a "later" item.

**Generated type shape.** Default to **operation-based, per-document-pruned codegen** (§0.1): one top-level class per operation, nested classes for its selection sets, scoped to only the schema types that operation actually references — never whole-schema upfront generation (graphql-code-generator's pre-v6 mistake) and never Apollo Kotlin's `responseBased` exponential-blowup mode. Represent every GraphQL union/interface as a **Dart sealed class hierarchy**, one subtype per possible concrete type, **plus a mandatory `Unknown` fallback variant** carrying the raw `__typename` and raw field map — this is the single most consistent convergent recommendation across every tool studied (Apollo Kotlin's `OtherHero`, Relay's `%future added value` + `__typename` union, cynic's `#[cynic(fallback)]`, graphql_client's `#[serde(other)]`). Back each generated selection-set type with a **shared decoded `Map<String, Object?>`** behind an `extension type` façade (Apollo iOS's `DataDict` trick, §3) rather than deeply-typed stored-field classes — this is what gives masking, type-casting, and test-mock generation for free via "re-wrap the same backing map as a narrower type," and Dart's extension types make this literally zero-cost (no vtable, no allocation), a genuine advantage over Swift/Kotlin which must still allocate wrapper structs/objects. Use **records** for transient, identity-less shapes (operation `Variables`, a `CacheKey(type, id)` pair) and **sealed classes/extension types** for the main Data model and anything needing discriminated-union or masking behavior — records cannot express sealed hierarchies.

**Fragment handling.** Pick exactly **one** masking mechanism and do not let a second one evolve independently (the lesson from Apollo Client v4 vs. graphql-codegen's documented incompatibility, §7): generate an opaque `extension type` per named fragment wrapping the same backing map, with an explicit unmask/read accessor function — the Relay/graphql-codegen `FragmentType`+`useFragment`/`readFragment` pattern, made zero-cost via Dart extension types rather than a TS phantom-type trick. Since Dart/Flutter has no JSX-equivalent file convention to colocate fragments in, treat Relay's "fragment colocation is mandatory" philosophy (§8) as an advisory lint rule (a `custom_lint` check flagging a widget that reads fields without declaring a fragment) rather than a hard requirement.

**Tri-state inputs.** Generate a sealed `Optional<T>` with exactly two variants — `Present(T value)` and `Absent` — where `T` itself is nullable for fields that allow explicit null. This matches both Apollo Kotlin's `Optional<T?>` and Apollo iOS's `GraphQLNullable<T>` precisely (§0.3): absence is `Absent`, explicit JSON `null` is `Present(null)`, a value is `Present(v)`. Do not model this as three separate enum cases.

**Scalar/enum policy.** Scalars: a minimal `ScalarCodec<T>` interface (`fromJson`/`toJson`), registered via a generated static map built from `build.yaml` config (schema scalar name → codec type), mirroring Apollo Kotlin's `Adapter<T>` (§2) — reflection-free either at compile time or via a runtime fallback map, with a dynamic/JSON-passthrough codec as the escape hatch for unmapped scalars (Apollo Kotlin's `AnyAdapter`). Enums: always generate a **sealed class**, never a plain Dart `enum` — one value object per known member plus a mandatory `UnknownEnumValue(String raw)` catch-all. This gives exhaustive `switch` and forward compatibility simultaneously, and Dart's sealed classes are strictly better suited to this than Kotlin's enum+sentinel-constant hack or Relay's string-literal-union+sentinel hack, since Dart already supports sealed-class exhaustiveness natively.

**Errors model.** Adopt the three-part response envelope — `data`, `errors`, `exception` (transport failure) — as a `GraphQLResponse<T>` class, matching Apollo Kotlin's `ApolloResponse` truth table (§2) exactly. As a v2 feature, support an opt-in `@catch`-style error-aware codegen pass (mirroring Apollo Kotlin's `@catch(to:)` and Relay's `@catch`/`@required`, §0.11) generating a `FieldResult<T>` sealed class (`Ok(T)`/`Err(GraphQLError)`) for fields marked nullable-due-to-error — reifying the error-vs-null ambiguity plain nullable fields can't express. Reject Kotlin's exception-unwinding `THROW` mode as a default: generated code should always reify a result, never throw mid-parse.

**Cache layering.** v1: an in-memory normalized `Store` — flat `Record` map keyed by cache ID, with a pluggable `CacheKeyResolver` (default `Type:id`, overridden via a generated `@typePolicy`-style directive/config plus a programmatic escape hatch, matching Apollo Kotlin/iOS's two-tier design, §0.6), mark-and-sweep GC rooted at retained active queries/subscriptions (Relay's `RelayModernStore`, §8), and an **optimistic-update overlay layer separate from the base store** for safe rollback (Relay's `RelayOptimisticRecordSource`). v2: a persistent backend (`sqlite3`/`drift`) chained behind the memory cache (Apollo Kotlin's `memCache.chain(sqlCache)`), with the on-disk format versioned conservatively from day one — Apollo Kotlin's own history of a destructive binary-schema migration between major cache versions (§2) is a direct cautionary tale to not repeat.

**Link/transport abstraction.** A chain-of-responsibility `GraphQLLink` abstract class returning `Stream<GraphQLResponse<D>>` (not `Future`, since `@defer`/subscriptions need multi-emission per request from day one — the mistake Apollo Client JS had to retrofit, which Apollo Kotlin's `Flow`-returning interceptor avoided by design, §0.8), composed via `Link.from([...])`, with named insertion points (`BeforeCache`/`BeforeAPQ`/`BeforeRetry`/`BeforeNetwork`) mirroring Apollo Kotlin's `InsertionPoint` enum so third-party links compose predictably. Subscriptions: `graphql-transport-ws` as the only v1 protocol (the actively maintained spec; skip legacy `subscriptions-transport-ws`, which Apollo Kotlin itself only keeps for backward compatibility) over `package:web_socket_channel`. `@defer`/`@stream`: v2, behind a pluggable `IncrementalDeliveryProtocol` interface (the spec isn't industry-stabilized yet — treat Apollo's `incremental/v0.2` as an interop target, not canon), surfaced as a plain `Stream<GraphQLResponse<D>>` with nullable-then-populated nested fields — never coupled to a UI-framework mechanism (reject Relay's React Suspense coupling, §8; Flutter has no equivalent). Uploads: the de facto [jaydenseric multipart request spec](https://github.com/jaydenseric/graphql-multipart-request-spec), used across Apollo iOS and the broader ecosystem. APQ: v1, both automatic persisted queries (hash-first, fallback to full body) and a build-time persisted-query manifest (hash→text map for safelisting) — pure transport/codegen concerns with no platform dependency.

**Test utilities.** v1: a schema-shaped fake-data builder (one function per schema type) with a pluggable `FakeResolver` interface (`resolveLeaf`/`resolveListSize`/`resolveMaybeNull`/`resolveTypename` — copy Apollo Kotlin's interface near-verbatim, §2), reusing the same backing-map trick as production models, plus a controllable in-memory mock `Link`/environment (mirroring Relay's `RelayModernMockEnvironment`, §8) so tests can resolve/reject specific operations and assert on exact pending requests.

**Compiler architecture & extensibility.** Structure codegen as two stages: (1) a whole-project aggregate builder phase that parses all `.graphql` files + schema into a single fragment/operation dependency graph, validating uniqueness and selections with did-you-mean diagnostics (the Relay lesson, §8 and §0.13 — required as soon as fragment reuse crosses file boundaries); then (2) a per-file emission phase producing one `.graphql.dart` part file per source file, pruned to only the referenced schema types (the graphql-code-generator v6 lesson, §4). Expose a stable `build.yaml`-registered `Builder`/`PostProcessBuilder` extension point from v1 as Dart's native, reflection-free answer to Apollo Kotlin's `ApolloCompilerPlugin`/`ServiceLoader` mechanism (§2, §0.15), so a normalized-cache package or custom ID-generation package can hook the pipeline without forking it — mirroring Apollo's own decision to split `apollo-kotlin-normalized-cache` out as a separate package in v5.

**v1 vs. later.**
- **v1**: `.graphql` + schema → build_runner codegen (document-first only) with a standalone-CLI wrapper around the same engine; operation-based, per-document-pruned output; sealed classes for unions/interfaces with mandatory `Unknown` fallback; sealed enum classes with `UnknownEnumValue` fallback; `Optional<T>` tri-state inputs; `ScalarCodec<T>` registry; single fragment-masking mechanism via opaque extension types; `GraphQLResponse<T>` envelope; in-memory normalized cache with declarative cache-key config + escape hatch, mark-sweep GC, optimistic overlay; `Stream`-based link chain with named insertion points; HTTP transport + `graphql-transport-ws` subscriptions + jaydenseric multipart uploads; APQ + persisted-query manifest; schema-shaped fake-data test builders + mock link/environment; `build.yaml` extension point for third-party builders.
- **Later (v2+)**: `@defer`/`@stream` incremental delivery (industry wire format still stabilizing); `@catch`/semantic-nullability error-aware codegen (`FieldResult<T>`) — valuable but spec-experimental even in Apollo Kotlin/Relay; persistent (`sqlite3`/`drift`) cache backend chained behind memory; cursor-connection pagination helpers (Relay-style `@connection`/`usePaginationFragment` equivalent); schema-aware partial-cache-result/stale-flag semantics (urql graphcache-style); fragment-colocation lint rule for Flutter widgets.
