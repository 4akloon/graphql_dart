# 02. The Dart GraphQL ecosystem

Date: 2026-10-13. Scope: every maintained (or recently maintained) Dart/Flutter package that touches GraphQL parsing, AST, schema/type-system, validation, execution, codegen, client, or transport, as of October 2026. Method: primary sources only — pub.dev package pages (fetched live), GitHub repository metadata via `gh api repos/...`, GitHub issue/search via `gh api search/issues`, and direct reads of source files via `gh api repos/.../contents/...` at the commit SHAs cited inline. Every non-obvious claim below carries a `file@sha` or `issue #N` or pub.dev link. Items that could not be verified within the GitHub Search API's rate limit are explicitly marked **UNVERIFIED**.

## 0. In brief

1. **`package:gql` is tooling, not a GraphQL implementation.** Its own source literally documents `GraphQLSchema` as "a GraphQL Schema definition **without** field resolution capacities" (`gql/lib/src/schema/schema.dart:9-10` @ `03c210f`, gql-dart/gql). There is no resolver model, no execution engine, no introspection runtime anywhere in the gql-dart org. Everything built on top (ferry, graphql_flutter, graphql_codegen) is a client; the only real *servers* in the ecosystem are leto, graphql_server2/angel3_graphql, and (dead) shelf_graphql.
2. **`package:gql`'s validator does not validate queries against a schema.** Only 9 validation rules exist, 8 of which check *internal SDL consistency* (duplicate type/arg/directive names, etc.) and exactly 1 touches executable documents (fragment-spread-target-defined). None of the ~25 other spec-mandated rules (`FieldsOnCorrectType`, `KnownArgumentNames`, `NoUnusedVariables`, `ValuesOfCorrectType`, `VariablesInAllowedPosition`, `OverlappingFieldsCanBeMerged`, `PossibleFragmentSpreads`, …) exist. This is confirmed by the maintainers' own still-open tracking issue, filed in 2019 and unresolved seven years later: gql-dart/gql#4 "Implement schema validation."
3. **Codegen tools each re-invent (buggy) type-checking** because the shared library gives them none. The single most-reacted-to open issue in `ferry` is a union-type codegen bug (ferry#306, 18 👍); interface/fragment interaction bugs recur across years (ferry#610, gql#228, gql#269).
4. **Union/interface `__typename` discrimination breaks under Flutter release/obfuscated builds** in *both* gql (gql#242) and ferry (ferry#319) — a repeated architectural mistake (discrimination keyed off Dart `runtimeType`/class names instead of an explicit string tag), not a one-off bug.
5. **`built_value`-based codegen is explicitly being abandoned by its own maintainers.** `gql-dart/ferry` is building `ferry_generator2` (pubspec v0.1.0-dev.7, no `built_value` dependency) whose README states its goal in plain words: "produces **plain Dart classes** (no `built_value`), with **small output** and fast builds" — a direct admission that output size and build speed were real problems (corroborated by ferry#143 "extremely slow build", 20 comments, and ferry#558 "Exponential complexity of unions generation").
6. **Automatic Persisted Queries are broken in the flagship client today.** `graphql_flutter`'s README marks `PersistedQueriesLink` "(experimental) ⚠️ **OUT OF SERVICE** ⚠️", with an unmerged migration PR open since v3 (zino-hofmann/graphql-flutter#699).
7. **`@defer`/`@stream` (incremental delivery) is unimplemented anywhere** in the Dart GraphQL ecosystem that this research could find; tracked as a still-open feature request even in the newer `leto` server (juancastillo0/leto#26, filed 2024-04-05).
8. **`graphql_flutter`'s own maintainers publicly flagged a bus-factor/maintenance risk** in a December 2025 issue titled "🚀 Revamping `graphql_flutter`: Roadmap, Community Involvement & Long-Term Maintenance" (zino-hofmann/graphql-flutter#1513) — the most important "is this safe to depend on long-term" signal found in this research.
9. **Some things are genuinely good and worth copying as *ideas*, not as dependencies**: gql's type-keyed heterogeneous `Context` bag (not a stringly-typed `Map<String,dynamic>` grab-bag), the `gql_tristate_value` 3-state (absent/null/value) wrapper for nullable input variables, GraphQL multipart-request file uploads (solid in `gql_http_link`/`gql_dio_link`), and explicit enum-fallback-value generation for unknown server enum values.
10. **Recommendation on AST compatibility with `package:gql`: ⚠️ adapt, do not inherit.** Build our own canonical AST (spec-shaped `NonNullTypeNode`, cached structural equality, full validation, real execution) as the source of truth, and ship a thin, separate interop/compat package that losslessly bridges to/from `package:gql`'s `DocumentNode` so we can plug into the existing `gql_link`/`gql_http_link`/`gql_websocket_link` transport ecosystem and ease migration off ferry/graphql_codegen. Making gql's AST *our* AST would permanently inherit its modeling and validation defects (see Defects catalog).

## 2. `package:gql` monorepo — deep source read (gql-dart/gql @ `03c210f`, 2026-06-17)

**AST** (`gql/lib/src/ast/ast.dart`): a single `@immutable` `Node` base class. Equality and `hashCode` are computed via `DeepCollectionEquality` over a freshly-built `_children` list *recomputed on every call* (ast.dart:39-56) — no memoization, no structural sharing/hash caching. `Request`/`Response` (gql_exec) reuse the same pattern for their own equality, and ferry/normalize lean on `Request`/`Response` equality for cache lookups and `rxdart` stream de-duping — meaning every cache hit test walks the whole document AST. No benchmarks were found to quantify the cost; flagging as a design smell rather than a measured regression.

**Nullability modeling**: no `NonNullTypeNode` wrapper as in the canonical spec AST (and graphql-js). Instead `TypeNode.isNonNull` is a boolean flag directly on `NamedTypeNode`/`ListTypeNode` (ast.dart:543-583). Functionally equivalent, but it is a non-canonical shape: tooling, fixtures, and mental models built against the spec's/graphql-js's three-node shape (`NamedType | ListType | NonNullType`) don't map 1:1.

**Interfaces/directives/extensions**: `interfaces implements interfaces` is modeled (`interfaces: List<NamedTypeNode>` on `InterfaceTypeDefinitionNode`, ast.dart:817+), repeatable directives are modeled (`DirectiveDefinitionNode.repeatable`, ast.dart:962, added per CHANGELOG `0.14.0`), and schema/type extensions exist (`SchemaExtensionNode`, `TypeExtensionNode`, ast.dart:642-1018). `@oneOf` input objects: **UNVERIFIED** — a targeted code search was rate-limited (GitHub Search API, 30 req/min) before it could be confirmed or ruled out; needs a follow-up check before deciding our own `@oneOf` scope.

**Visitor/transformer** (`ast/visitor.dart`, `ast/transformer.dart`): `Visitor<R>` is a fully-abstract class with ~40 `visit*` methods and *no default bodies* — any custom typed visitor must implement every node type. Three convenience subclasses exist and are genuinely usable: `SimpleVisitor<R>` (nullable return, visitor.dart:229), `RecursiveVisitor` (void, auto-recurses into children, visitor.dart:500), `AccumulatingVisitor<A>` (collects into an accumulator, visitor.dart:772). `TransformingVisitor` (transformer.dart:23+) gives every node a pass-through default, which is why AST *transforms* are more pleasant to write than AST *analyses*.

**Lexer/parser** (`language/lexer.dart`, `language/parser.dart`): block strings with correct dedent logic exist (`dedentBlockStringValue`, lexer.dart:531+). Errors are `SourceSpanException`s carrying real source spans (e.g. parser.dart:61,84,175,...), so location-aware error messages are a solved problem here. Two concrete spec-compliance gaps found by reading the lexer directly:
- Only the fixed 4-hex `\uXXXX` escape is implemented (`RegExp(r"\\u[0-9A-Za-z]{4}")`, lexer.dart:74-88); the GraphQL (post-June-2018) variable-length `\u{XXXXXX}` escape for non-BMP/astral code points is not implemented at all.
- `char2Hex` (lexer.dart:515-528) returns `-1` silently for a non-hex character instead of raising a syntax error, so a malformed escape such as `\uG123` is *accepted* by the regex (`A-Za-z` matches more than hex digits) and silently decodes to a bogus code point rather than failing with a located parse error.
Parsing fails fast on the first syntax error (no multi-error collection) — standard for GraphQL parsers, but worth a deliberate choice for us since collecting multiple syntax errors per document is valuable for LSP/IDE tooling.

**Validation** (`validation/rules/*`, 9 files total): `lone_schema_definition.dart`, `missing_fragment_definitions.dart`, `unique_argument_names.dart`, `unique_directive_names.dart`, `unique_enum_value_names.dart`, `unique_field_definition_names.dart`, `unique_input_field_names.dart`, `unique_operation_types.dart`, `unique_type_names.dart`. Eight of these are SDL/type-system-document internal-consistency checks; exactly one (`missing_fragment_definitions`) is an executable-document rule (fragment spread target defined). **None** of the ~25 other spec-mandated executable-document rules exist (no `FieldsOnCorrectType`, `KnownArgumentNames`, `NoUnusedVariables`, `NoUndefinedVariables`, `ValuesOfCorrectType`, `VariablesInAllowedPosition`, `OverlappingFieldsCanBeMerged`, `PossibleFragmentSpreads`, `KnownDirectives`, `UniqueVariableNames`, `SingleFieldSubscriptions`, etc.). Confirmed independently by the still-open gql-dart/gql#4 "Implement schema validation" (filed 2019-10-03).

**Schema/execution** (`schema/schema.dart`): `GraphQLSchema` is explicitly documented "without field resolution capacities" (schema.dart:9-10). There is no execution engine, no resolver pipeline, and no introspection-query runtime anywhere in gql-dart/gql. This is a deliberate scope boundary, not an oversight — but it means "gql" answers none of "execution/server" in this research brief; that's entirely the leto/angel3/graphql_server2 story (see §4).

**Request/Response/Context/Errors** (`links/gql_exec/lib/src/*`): `Context` is a type-keyed heterogeneous bag, `Map<Type, ContextEntry?>` (context.dart) — genuinely good, type-safe design, not a stringly-typed grab bag. `Request.variables` and `Response.data`/`Response.response` are plain `Map<String, dynamic>` (JSON leaks into the public low-level API — expected at this layer, but `Response` keeps three overlapping representations — raw `response`, parsed `data`, parsed `errors` — that every terminating link must keep in sync). `GraphQLError.path` is `List<dynamic /* String | int */>` (error.dart) — a comment, not a real union type. `LinkException` hierarchy (`gql_link/lib/src/exceptions.dart`) is reasonably clean (`RequestFormatException`, `ResponseFormatException`, `ServerException`, `ContextReadException`, `ContextWriteException`), but the primary downstream consumer doesn't trust it yet: `graphql_flutter`'s own source comment reads "Once `gql_link` has robust http and socket exception handling, these should be the only exceptions we need" (`packages/graphql/lib/src/exceptions/exceptions_next.dart`, zino-hofmann/graphql-flutter) — and then layers ~8 more exception types on top (`CancelledException`, `CacheMissException`, `MismatchedDataStructureException`, …).

**File uploads**: solid. GraphQL multipart-request-spec uploads are implemented and tested in both `gql_http_link` and `gql_dio_link` (`links/gql_http_link/lib/src/link.dart`, `links/gql_dio_link/lib/src/dio_link.dart`, with `multipart_upload_test.dart` in both) and consumed by `graphql`. Worth reusing the protocol approach, not the code.

**Persisted queries**: not implemented in gql-dart/gql itself. In `graphql_flutter`, `PersistedQueriesLink` is explicitly marked "(experimental) ⚠️ **OUT OF SERVICE** ⚠️" in the current README, citing an unmerged migration PR (zino-hofmann/graphql-flutter#699) open since the v3→v4 transition.

**`@defer`/`@stream`**: no code hits anywhere in gql-dart/gql; no implementation found in `graphql`/`graphql_flutter` either. The clearest evidence is a still-open feature request in `leto` (juancastillo0/leto#26, filed 2024-04-05): incremental delivery is unimplemented across the Dart GraphQL ecosystem as far as this research could determine.

## 3. Ferry — deep read (gql-dart/ferry @ `cccabf8`, 2026-07-05)

`ferry` (core client, pubspec: `dependencies: built_value: ^8.0.4`, plus a direct `hive: ^2.0.0` dependency in the *core* package even though opt-in store packages exist — `ferry_hive_store`, `ferry_sqlite_store`, `ferry_hive_ce_store`) is the most popular typed client (369 likes) and the most actively discussed (102 open issues). Its generator (`ferry_generator`, built_value-based) is in the process of being replaced: the repo already contains `ferry_generator2` (pubspec v0.1.0-dev.7, dependencies `code_builder`, `dart_style`, `gql_tristate_value` — **no `built_value`**). The `ferry_generator2` README states its purpose directly: "produces **plain Dart classes** (no `built_value`), with **small output** and fast builds," supports "Interfaces/unions with sealed class hierarchies and `__typename`," tri-state variables via `gql_tristate_value`, scalar overrides, and global/per-enum fallback values. This is the clearest first-party admission in the whole ecosystem that the old codegen's output size and build speed were real, serious problems — directly corroborated by:
- ferry#143 "extremely slow build" (10 👍, 20 comments, open since 2021)
- ferry#558 "Exponential complexity of unions generation" (4 👍, 16 comments, 2023)
- ferry#622 "Ferry Generator 2.0" (38 comments, open since Feb 2025 — the design discussion that produced generator2)

Recurring union/interface/fragment codegen bugs, all independent issues over 3+ years, point at a systemic gap rather than isolated bugs: ferry#306 "Bug when generating the classes of fragments with a union type" (18 👍, the single most-reacted open issue in the repo), ferry#319 "Union type issue for flutter web on release build mode" (8 👍 — obfuscation breaks type discrimination, same root cause as gql#242), ferry#610 "Fragments not working with interfaces" (2024, 14 comments), ferry#219 "Nullable list generated as an empty list" (null vs. empty-list confusion, directly relevant to nullable/tri-state handling). No request cancellation exists: ferry#344 "[Proposal] Allow user to cancel request" (8 👍, open since 2022).

`normalize` (the normalization/denormalization engine backing ferry's cache) is stable and reasonably well-liked; no major open defects surfaced in this research pass beyond what's already covered by ferry's own union/interface bugs (normalize is where those bugs ultimately manifest as cache corruption).

## 4. graphql / graphql_flutter (zino-hofmann, formerly zino-app)

The most-downloaded client (`graphql` 469k weekly, `graphql_flutter` 244k weekly) and the most-starred repo (3268★), but also carrying the most open issues (167) and the clearest public maintenance-risk signal in this research: zino-hofmann/graphql-flutter#1513, "🚀 Revamping `graphql_flutter`: Roadmap, Community Involvement & Long-Term Maintenance" (opened 2025-12-18, still open). Other long-standing, highly-reacted gaps: #1457 "Timeout should be handled by the http client not the library" (13 👍, 26 comments, 2024, still open), #712 "Consider moving to dio over http client" (16 👍, open since 2020), #877 "None GraphQL server error message not part of Exception" (12 👍 — an error-model complaint consistent with the `gql_link` robustness comment found in-source), #543 "Query never ends if network gets disconnected" (12 👍), #333 "refetchQueries option for client.mutate" (12 👍, a long-missing Apollo-Client-parity feature), #424 "Isolate the GraphClient in another thread" (27 comments — no off-main-isolate execution model).

## 5. Artemis — discontinued

`artemis` (comigor/artemis) is **archived on GitHub** and **marked discontinued on pub.dev**, pointing users at Ferry as the replacement. Last commit to its default branch (`beta`) was 2023-10-06. 491★, 48 open issues, frozen. Historically it generated types from introspection (`schema.graphql` + `*.graphql` files), which is architecturally interesting (schema-aware codegen without a shared validator) but not something to depend on. ❌ avoid as a dependency; worth skimming its introspection-driven codegen approach as prior art only.

## 6. graphql_codegen (heftapp) — the best current codegen UX

`graphql_codegen` (heftapp, v3.0.2, 152 likes, 201k weekly downloads, publisher `heft.app` verified) deliberately avoids `built_value`, using `json_serializable`/`json_annotation` instead (pubspec confirmed: `built_collection` is a transitive dep via `gql_code_builder`, but the generated-code strategy is json_serializable-based, not built_value-based). It still runs on `build_runner`, so the generic Dart tooling pain (`build_runner` being slow, especially on large projects) is not avoided — that pain is a Dart-ecosystem-wide issue, not specific to one codegen tool. Open requests show the same shape of gaps as ferry: #322 "Add support for multiple module projects" (6 👍, 14 comments), #343 "Remove edges and node from parsed data" (Relay-style connection boilerplate), #344 "Option to make Variables$ required".

## 7. Server side: leto, angel3/graphql_server2 line, shelf_graphql

**leto** (juancastillo0/leto) is the most architecturally serious Dart-native execution engine found (framework-agnostic executor + `leto_schema` type system + `leto_shelf` HTTP/WS/upload server), but it has never left `0.0.1-dev.x` after 3 years, has only 6 contributors, 42★, and its default-branch HEAD was last touched 2023-11-24 (repo `pushed_at` shows 2024-06-20, likely a non-default branch or tag). Its own open issues read like a checklist of exactly the gaps this research is looking for: #26 "GraphQL @defer and @stream" (open, 2024-04-05), #24 "Differentiate between null and undefined" (open, 2024-02-01 — the tri-state problem, unsolved even server-side here), #2 "Feature Request: Federation Support" (open), #9 "Multithreading support" (open). Worth a careful read as prior art for our own execution engine design, not as a dependency.

**angel3_graphql / graphql_schema2 / graphql_server2 / graphql_parser2** (all under `dart-backend/graphql_dart`, the actively-maintained Angel3-successor org, `dukefirehawk.com` verified publisher) were *all* released at v7.0.0/v9.0.0 only 53 days before this research (~August 2026) — more recently active than leto, but download counts are tiny (hundreds/week) and the whole line is coupled to the niche Angel3 server framework. `graphql_schema` (the pre-"2" predecessor, angel-dart/graphql) is dead (v1.0.4, 7 years old, 0 likes, 43 weekly downloads).

**shelf_graphql**: the one maintained by juancastillo0 is effectively folded into `leto_shelf`; the independent `Flutterando/shelf_graphql` fork is archived (2022). Dead end.

## What to reuse

- **`Context` as a type-keyed heterogeneous bag** (`Map<Type, ContextEntry?>`, `gql_exec/lib/src/context.dart`) — ✅ take the pattern (not the code): type-safe request/response metadata without stringly-typed maps.
- **`gql_tristate_value`-style absent/null/value wrapper** for nullable GraphQL input variables — ✅ take the concept; implement as our own sealed 3-state type rather than a generic wrapper class, so pattern-matching is exhaustive at compile time.
- **GraphQL multipart-request file uploads** (`gql_http_link`, `gql_dio_link`) — ✅ take the protocol/spec conformance approach; it is one of the few unambiguously solid corners of the ecosystem.
- **Enum unknown-value fallback generation** (gql CHANGELOG `0.12.4`; `ferry_generator2`'s global/per-enum fallback) — ✅ take directly; generate an explicit sentinel member instead of throwing on unrecognized server enum values.
- **`ferry_generator2`'s stated design goals** (plain Dart output, no reflection/builder framework, small generated surface, sealed hierarchies for unions/interfaces with explicit `__typename`) — ✅ take as a north star for our own codegen, even though the package itself is pre-release and not a dependency.
- **AST compatibility with `package:gql`: ⚠️ adapt via a thin interop/bridge package, do not make it our core AST.** Build our own canonical, fully-validated, execution-capable core; ship a separate `*_gql_compat` package translating to/from `package:gql`'s `DocumentNode` for the common subset, so we can (a) plug into the existing `gql_link`/`gql_http_link`/`gql_websocket_link` transports during migration, and (b) let existing ferry/graphql_codegen users adopt our parser/validator incrementally without a flag-day rewrite. Full dependence on gql's AST would permanently inherit D3/D4/D5/D1/D2 above; full avoidance would forfeit the only real interop story with the existing Dart GraphQL tooling (build_runner builders, existing transports, existing production apps).
- **`built_value` and `build_runner` as hard dependencies** — ❌ avoid for our own codegen; both the ecosystem's own migration (ferry → ferry_generator2) and the standing complaints (ferry#143, #558) point the same direction.

## Open questions

1. Whether `@oneOf` input objects are supported anywhere in the Dart GraphQL ecosystem is **UNVERIFIED** — a targeted GitHub code search was rate-limited before it could be confirmed or ruled out. Needs a follow-up check (or a direct read of `gql/lib/src/ast/ast.dart`'s `InputObjectTypeDefinitionNode`/directive-location enum for an `ONEOF`-shaped location) before finalizing our own `@oneOf` scope.
2. Whether to target `build_runner`/`build.yaml` compatibility for ease of migration from ferry/graphql_codegen, or to ship a standalone codegen CLI that bypasses `build_runner` entirely — `build_runner` itself is a widely-cited pain point ecosystem-wide (not just for gql-based tools), so bypassing it may be a bigger win than any AST/validation improvement.
3. Whether to pursue Apollo Federation support at all — explicitly requested and unresolved in `leto` (#2) and absent everywhere else; needs an explicit scope decision (in vs. out of v1) rather than an implicit "maybe later."
4. What the concurrency/cancellation model for both client and server should be (Isolates? structured concurrency? `CancellationToken`?) — every existing client in this research either lacks it (ferry#344) or pushes it onto the underlying HTTP client in a way users dislike (graphql_flutter#1457, #424). Worth deciding before any execution-engine or client code is written, since retrofitting is expensive.
5. The precise pub.dev like/points/download figures in §1 were extracted via an LLM-summarized page fetch rather than pub.dev's JSON API, and pub.dev itself mixes "weekly" and apparently-"total" download labels inconsistently across package pages — treat all numeric figures above as order-of-magnitude, and re-scrape precisely (e.g. via pub.dev's API endpoints or a direct HTML parse) before using them in any external-facing comparison document.
6. `juancastillo0/leto`'s repo-level `pushed_at` (2024-06-20) does not match the default branch's HEAD commit date (2023-11-24) found when reading source — likely a push to a non-default branch, a tag, or a GitHub Pages deploy; not investigated further. Treat "leto" as roughly 2+ years stale, but note the exact last-activity date is slightly uncertain.
